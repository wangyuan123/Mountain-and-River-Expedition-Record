# 军团驻军协同防守实施验收记录

日期：2026-10-24。规则版本：`joint-defense-v1-20261024`，数据库迁移：V126。对应 [设计文档](../../docs/GUILD_GARRISON_JOINT_DEFENSE_DESIGN_20261024.md) 第16～17节。

本轮代码回归、独立 MySQL 实战、战报权限、接收城粮耗、缺粮返程及最终资产归还均已完成。以下分别说明实测证据和验证边界，不将自动测试等同于所有场景的浏览器人工实测。

## 1. 实施范围

- 本城按自身迎战预设选兵，有效且已到达的驻军全量额外参战；战中迟到者不加入本场。
- 同一场战斗保留每支行军身份与随队军官，采用守城公共科技及城市司令官，随队军官、装备和技能限定本来源。
- 按来源独立记录技能周期，同兵种统一指挥、同步机动，同条件协同伤害逐目标统一提交，有限反击后再处理幸存者余伤。
- 按来源保存实际战损、伤兵、幸存和伤害贡献；日志保留“【本城·守将…】／【援军·玩家…·将领…】”格式，区分机动时和交火时数量。
- 接收城承担驻防粮耗，每城独立接收设置，缺粮拒收、未参战整队返程、已参战待终局评估；派兵城不重复计同段驻防粮耗。
- 原派兵城失守保留活动来源至终局，原玩家资产合法返程或保存待安置状态；医疗按终局采样。
- 战报和战场接口按角色裁剪，分享单独采用公开字段白名单；旧会话、旧战报与旧驻军计费起点保留兼容。

首版未新增驻防容量限制、额外援军将领俘虏规则或独立侦察军官新模型，符合设计范围。

## 4. 战报权限、粮耗与最终归还

- 三个账号读取各自战报详情，均只获得属于自己的终局医疗采样；攻方和城主各1行，派兵人2行。完整敌方军官和兵种配装字段不透传。
- 攻方尝试按ID读取城主战报被拒绝。通过临时凭证核验分享公开投影，递归检查不包含内部城市、军官、医疗及坐标字段。临时凭证用后删除，未发送聊天分享消息。
- 正式接收设置入口结清实际经过的游戏时间：接收城粮食从999,462,741降至996,115,983，派兵城保持1,000,000,000；驻军粮耗7,979,192／小时，本城库存粮耗1,600,000／小时。
- 经用户单独授权清空合成接收城粮食后，两支驻军整队转为返程，幸存兵力保持498,341和499,058，接收城外来驻军粮耗归零。未满足需求记录只作历史短缺记录，不构成债务。
- 两支合成返程时间缩短后，8082关闭调度，读取状态不会结算返程。因此另启8083连接同一独立库并恢复正常调度，未停止原服务或8082，未再次修改行军时间。
- 由正常 `TickScheduler` 完成最终归还：原派兵人获得997,399辆重坦，两支行军记录清除，两名随队军官均为 `idle`；本城库存仍为200,000。`997,399幸存 + 2,601战损 = 1,000,000初始驻军`。

原始证据：`06-report-detail-*.json`、`07-other-player-report-denied.json`、`08-shared-public-report.json`、`09-food-accounting.json`、`10-famine-return.json`、`11-return-conservation.json`、`return-verification.log` 和 `backend-scheduled.log`。

早先验收脚本断言因游戏时钟未跨调度周期、接口已删除内部 `playerId`、以及手动环境未启用业务调度而失败，相关原始日志保留；后续读取实际状态并完成上述核验。未将失败断言覆盖解释成测试通过。`verify_postbattle.py --verify-return-only` 提供最终只读资产复核入口。
