# 聊天、邮件与战报保留及清理方案

日期：2026-10-21。状态：设计提案，尚未实现。本文不代表已启用过期规则或已清理历史数据。

## 1. 目标与依据

优先解决全量读取历史数据造成的请求内存膨胀，以及聊天限流计数不淘汰的问题；随后建立明确的数据保留期限，让数据库中的普通历史记录可持续周转。

当前实现的关键事实：

- 世界、军团聊天从数据库读取最近 50 条，浏览器各保留最多 80 条；数据库没有按时间清理。
- 私聊读取最近 50 条。删除会话和清空内容只是当前账号的可见性边界，不物理删除双方消息。
- 邮件支持收件人手动删除，但邮件列表没有数据库分页。目前没有附件到期字段，系统/奖励等展示分类也不足以区分节日赠礼和已取得资产。
- 普通战报接口先查询玩家全部战报，再截取最多 200 条；战报包含完整 JSON 和回合日志。
- PvP 演习结算时清理第 51～100 条个人报告；不能由此认定演习会话、指令和逐回合结果已经清理。
- `RateLimiter` 的计数键不移除；世界聊天每天生成新的日期键。两个公开聊天服务的防重复消息 Map 也没有过期淘汰。
- 普通战报分享只有主体引用，没有过期时间；军情分享保存独立快照，也没有过期时间。

2026-10-21 本机开发库取样：普通战报 157 份，JSON 内容约 5.46 MiB，平均约 35.6 KiB/份，最大约 246 KiB/份。该取样只用于评估字段体积，不代表线上容量或增长速度。

## 2. 建议默认保留规则

下表的“天”均指真实经过的 24 小时，由服务端真实时间计算。阈值允许通过配置调整，读取时的过期判断与后台清理必须共用同一套策略。

| 数据 | 默认规则 | 保护与用户可见行为 |
| --- | --- | --- |
| 世界聊天，包括频道系统广播 | 保留 7 天 | 历史区说明保留期限；首次仍加载最近 50 条 |
| 军团聊天 | 保留 30 天 | 军团解散、成员退出等现有权限规则保持独立 |
| 私聊消息 | 保留 90 天，已读、未读适用相同期限 | 到期同时从双方历史移除；提前清空仍只影响操作者本人 |
| 已读且没有待领取附件的邮件 | 满足“已读、附件已处理且关联业务结束”后保留 30 天 | 领取一封很旧的邮件后仍有完整保留期，不会当天被清理 |
| 未读且没有待领取附件的邮件 | 从实际收件时间起保留 60 天 | 邮件列表说明未读邮件也有期限 |
| 节日、登录等明确限时的主动赠礼 | 默认活动结束后 30 天未领取即失效 | 活动期登录才发放，每账号每大区每活动一份；到期显示失效，7 天后清理邮件 |
| 购买、补偿、退还、已结算战果及玩家转赠等资产附件 | 未领取前不按年龄自动删除 | 根据可信业务来源保护，不因玩家离线而失效；单独统计积压 |
| 普通战报完整详情，含侦查、野地、城市战、拦截 | 保留 30 天 | 此后保留摘要，详情区明确显示“详细日志已过期” |
| 普通战报摘要 | 完整详情到期后再保留 30 天 | 战报最多可看 60 天；之后移除摘要，并重新计算未读数量 |
| 收藏战报 | 每个账号、每个大区最多 50 份，收藏期间保留摘要和详情 | 只能收藏仍有完整详情的战报；到达限额后需先取消已有收藏 |
| PvP 演习个人战报 | 保留最近 50 份，且最长 30 天，以先达到者为准 | 同时补齐底层演习数据的关联清理规则 |
| 普通战报分享凭证 | 自分享起最长 7 天，并受原战报剩余详情保留期限制 | 收藏不延长已经发出的分享链接；过期显示“分享已过期” |
| 来袭军情分享快照 | 自分享起保留 24 小时 | 明确显示快照时间；行军结束不把历史快照误写成实时军情 |

补充约束：

1. 收藏属于战报接收账号，不改变对方的保留期限。取消收藏后恢复原到期规则；若原期限已过，界面提前说明将按过期记录处理。
2. 战报未读状态不豁免日志过期或摘要过期，否则长期离线账号会无限积累记录。上线时先提供明确的保留说明和历史过渡期。
3. 邮件当前由收发双方共用一行记录，到期物理清理后也不再出现在发件箱；规则在收件箱、发件箱入口统一说明。
4. 有效中的劝降、城市移交等业务关联邮件暂不清理，即使邮件已读；须先确认关联业务终结，再进入普通邮件保留流程。这里保护的是关联业务状态，不能仅依靠邮件类型字符串判断。
5. 如果未来新增申诉留存或管理员冻结标记，该标记必须有明确的操作者、用途和解除流程；第一版不加入无期限的自动保护分类。
6. 限时赠礼的到期规则优先于普通邮件的已读/未读保留期；未领到期后不能再进入“未读保留 60 天”流程。已领取的赠礼按普通已处理邮件保留 30 天。
7. 不能仅凭 `is_system`、`type=reward`、邮件主题或离线时长判断附件可以过期。来源或原约定不明的旧附件暂按受保护资产处理；新赠礼必须由业务显式声明限时策略。

这套方案约束普通历史记录及限时赠礼的增长。受保护资产附件、尚未确认来源的旧附件、收藏限额内的战报、战斗结算凭证属于明确保留的例外，不能宣称整个数据库从此不再增长。

## 3. 先修读取方式，再启用历史清理

### 3.1 数据库分页

- 战报、邮件默认每页 20 条，最大 100 条；聊天历史默认每次 50 条，最大 100 条。
- 使用稳定游标，例如 `(created_at, id)`，不通过越来越大的 OFFSET 翻页；查询始终带登录账号、军团或私聊参与者约束。
- 返回 `{ items, nextCursor, hasMore, retentionPolicy }`。接口变更通过新版本或兼容参数分阶段接入，不能直接破坏现有数组调用方。
- 使用数据库 DTO/投影明确选择摘要字段；仅增加 `PageRequest` 但继续加载 `LONGTEXT` 不算完成列表优化。
- 未读数量在数据库聚合；“全部已读”通过带账号条件的更新完成，不逐条加载邮件、战报正文。
- 超过可见期限但尚未物理删除的记录不进入列表、详情或未读统计，因此后台任务短暂落后不会造成界面反复出现过期数据。限时赠礼的领取截止与邮件可见期限分开：附件到期后有 7 天失效说明期，期间可见但不可领取、不计入待领取数，说明期结束再从列表及未读统计移除。
- 私聊查询在数据库内同时应用参与者条件、当前账号的清空边界和保留条件，再进行分页；不能先读取一页再在 Java 中过滤。

### 3.2 列表与详情分离

战报列表只返回目标、时间、动作、接收者视角、胜负、兵力概览、收藏和详情可用状态。点击展开时，按 ID 单独请求详情并校验归属；分享入口通过原有随机凭证校验读取。

邮件列表只返回发件人、主题、预览、时间、已读和附件状态；打开邮件后读取正文及附件。列表接口不返回全部正文，前端也不累积所有已翻过页面。

### 3.3 浏览器缓存

- 保持世界、军团聊天各 80 条，单个私聊当前显示 50 条的现有上限；翻页历史只保留有限窗口。
- 战报最多缓存 100 条摘要；详情最多缓存 5 份，且合计不超过 5 MiB，超限时淘汰较早查看的详情。
- 邮件保留当前列表页和当前打开的正文。
- 详情、分页游标和未读状态按账号、大区隔离；切换账号、大区或退出登录时清除。
- 接口返回记录过期时同步移除对应缓存；重连、返回列表时刷新统计，离线页面也不能靠永久缓存保留已失效分享。

## 4. 战报采用摘要与完整详情分层

第一版可复用 `scout_reports` 表，避免立即引入归档服务：

- 增加 `summary_json`，以及可用于投影的必要摘要字段。
- 原 `data` 继续保存完整快照，战报保存满 30 天时清空详情；摘要再保留 30 天，到期后删除摘要行。普通战报总可见期最多 60 天。
- 增加 `persisted_real_at`、`detail_expires_at`、`summary_expires_at`、`starred_at`、`summary_schema_version` 和过渡保护信息。
- 收藏时清除自动到期值或由统一策略排除收藏记录；取消收藏时根据原始持久化时间恢复到期值。
- 报告生成和结算在原事务内同时保存摘要、完整详情和期限，任何一部分失败时共同回滚。

摘要保留当场记录的攻守身份、双方初始/幸存兵力、战损与伤兵/俘获概览、将领姓名、资源和声望变化、实际胜负及部队去向。摘要只作为历史展示，不参与重新发奖、重新扣兵或重新结算。

旧战报有依赖回合日志恢复兵力和名称的兼容逻辑。必须先从原始快照和日志生成完整、可验证的摘要，才允许裁剪详情；不能先删日志后让前端用当前兵种或当前将领配置推测历史。无法可靠生成摘要的旧记录暂时跳过并告警，不能静默丢失兵力信息。

摘要阶段的接口明确返回 `detailsAvailable=false` 和过期原因；战报卡片仍可查看战果，不展示“暂无回合记录”这种容易被理解为战斗数据缺失的提示。

这一阶段无需同时重构“同一场战斗供双方共享一份详情”的存储模型，先解决保留与按需加载，降低对既有视角和分享功能的影响。

## 5. 时间口径与旧数据迁移

当前 `created_at` 不统一：聊天、私聊、邮件使用真实时间，普通战报及演习使用 `GameClock.now()`。游戏时间会在停服期间暂停，不能拿这些历史字段直接与真实当前时间相减决定是否删除。

- 新记录使用单独的 `persisted_real_at` 或明确的 `*_real_at` 字段管理生命周期，历史显示时间继续保持原值。
- 后台运维任务按真实时间调度，不占用游戏时钟线程，也不随游戏进度暂停；停服期间没有任务执行，恢复后仍按分批预算处理已经到期的历史数据。
- 邮件增加可恢复的 `processed_real_at`：仅当已读且没有待领附件，并且关联业务已结束时进入普通清理期限；再次发生影响资格的状态变更须重新计算。
- 限时赠礼单独记录附件领取截止时间和失效状态；到期未领走失效后 7 天清理流程，不借用 `is_claimed` 表示失效，也不按普通已处理邮件重新计时。
- 没有可信真实时间的旧战报，以规则启用时刻作为保守的保留起点：旧详情再保留 30 天，随后摘要保留 30 天；不根据当前游戏时钟偏差反推真实创建日期。
- 旧版已读、附件已处理邮件缺少准确处理时间，以规则启用时刻作为 `processed_real_at`。
- 旧聊天、未读且无待领附件的邮件可沿用可信真实创建时间，但统一给予至少 7 天的上线过渡保护期。
- 旧版未领取附件不能整体套用限时赠礼规则。只有通过可信业务记录确认属于主动赠礼、完成影响统计并公布变更后，才可单独迁移为至少 30 天的领取宽限期；无法确认的继续保护，不凭标题或年龄推断。
- 没有真实分享时间的历史分享凭证，统一在规则启用后 7 天到期；这是一次性迁移规则，不覆盖新军情快照的 24 小时期限。

默认保留期由配置决定，新记录保存明确的到期时刻。后续配置调整默认影响新记录；如需缩短已有记录的期限，必须作为单独的数据迁移评估，不随服务重启立即追溯缩短。紧急停止物理清理使用独立开关；需要延长用户访问期限时同步调整到期策略，不能把“暂停物理删除”误当成“延长可见期”。

## 6. 内存计数与防重复消息淘汰

限流器继续适配当前单实例部署，第一版不以引入 Redis 为前提：

- 每个计数器持有明确的窗口截止时间；每分钟分批淘汰真正已到期的计数器。
- 同一键的计数更新与过期淘汰使用原子操作，不能在刚开启新窗口时删除新计数，让用户绕过限流。
- 每日聊天额度保留当前按真实北京时间日期生成键的语义；旧日期键无需永久保存。
- 计数键默认容量上限为 100,000。达到上限先清理过期项，仍不足时对需要新增键的请求返回可重试的限流结果；不通过淘汰仍有效的计数器重置额度。
- 世界、军团防重复消息记录在最后发送 2 分钟后可淘汰，仍保留原有 60 秒重复内容保护。
- 定期记录计数键数、过期淘汰数、容量拒绝次数，不记录玩家消息原文。

未来真正部署多个业务实例时，再将限流状态迁移到支持原子操作的共享存储；数据库清理不依赖这个迁移。

## 7. 后台清理的执行方式

### 7.1 调度与预算

使用独立的单线程维护调度器，每 10 分钟检查到期记录。不要将清理工作挂到当前只有一个线程的 `taskScheduler` 或游戏时钟线程上。

默认参数：

| 参数 | 默认值 |
| --- | --- |
| 数据库清理间隔 | 10 分钟 |
| 单批候选记录 | 200 条 |
| 每个类别单轮最多处理 | 1,000 条 |
| 单轮总时间预算 | 5 秒；每批之间检查，单条 SQL 另设超时 |
| 内存过期扫描间隔 | 1 分钟 |
| 发布观察期 | 至少 7 天，仅统计、不删除也不裁剪详情 |

每批独立事务，达到预算后保存进度并在后续轮次继续；各类别轮转，不能因某张表积压而长期跳过其他类别。失败记录不阻塞整轮，保留日志供后续重试。

多实例通过数据库维护任务租约，保证同一类别同一时段只有一个执行者；租约到期可恢复，提交和续租校验持有者。第一版即可保留这一边界，避免未来扩容后重复扫描与锁竞争。

### 7.2 查询与并发

- 先按索引有界选择候选 ID，不把所有正文加载进 Java 内存。
- 实际更新或删除时，在同一事务内再次验证到期、收藏、附件和关联业务状态，不能只依赖先前查询的快照。
- 收藏与详情裁剪对同一报告加行锁并复核：若清理先提交，收藏返回“详情已过期”；若收藏先提交，清理跳过。禁止出现“已收藏成功但详情被清空”。
- 邮件清理与领取附件遵循相同锁顺序，领取失败不推进已领取状态或普通清理期限。
- 限时赠礼在持有领取所需锁后，以服务端真实时间复核领取截止时间；领取裁决时刻早于截止时间才可入账，达到截止时间即拒绝。清理尚未执行不能成为领取过期附件的途径，锁等待也不能绕过到期判断。
- 不把游标当成永久跳过记录的依据。因保护条件而跳过的记录，保护解除后必须重新进入候选；完成一轮后回到起点，或维护可重新索引的到期时间。
- 关注到期索引、所有者分页索引及必要的复合条件；通过执行计划和代表性数据验证，无须给所有字段盲目加索引。

建议索引包括：聊天消息到期时间及 ID、军团与时间及 ID、私聊双方与 ID、邮件收发人及时间、邮件清理到期时间、战报接收人及时间、详情/摘要到期时间、分享凭证到期时间。具体索引取舍以实际查询及既有索引为准。

### 7.3 可见期与物理删除

到期时间是产品规则，后台任务执行时间是回收实现。读取接口即刻判断是否到期，物理清理可在后续批次完成。

普通战报分享使用 `min(分享时间 + 7 天, 原详情到期时间)`；已收藏主体在生成新分享时最多获得新的 7 天有效期。过期凭证读取统一返回明确的过期状态，并保留原本的登录、归属或军团权限校验；后台随后删除凭证。权限校验不能因为启用了过期机制而放宽。

删除战报摘要时同步清理引用型分享记录。军情分享是独立快照，要单独按到期索引清理，不能等待原行军或个人战报删除。

## 8. 附件、演习与结算凭证的边界

### 8.1 邮件附件

附件采用两类策略，不能继续使用“所有未领附件永久保留”的统一规则：

| 策略 | 适用来源 | 生命周期 |
| --- | --- | --- |
| 限时主动赠礼 | 节日礼包、登录赠礼等事先明确领取期限的福利 | 到期未领则失效，失效后 7 天移除邮件；已领按普通已处理邮件保留 30 天 |
| 受保护资产 | 购买、补偿、交易/行军退还、已结算战果、玩家已扣款转赠，以及来源不明的旧附件 | 领取权利不因长期离线自动消失；通知与资产资格未来可拆分保存 |

**节日赠礼的默认发放方式：**

- 保存一份大区活动定义与奖励快照；玩家在活动窗口内登录时才生成个人邮件，不向所有历史账号预先插入一封邮件。
- 以账号、大区、活动 ID 建立唯一领取资格/发放记录；重复登录、重试或邮件被手动删除都不能再次生成奖励。
- 领取截止时间统一为活动结束后 30 天，并在活动入口和邮件中展示。活动结束后才回归的玩家不补发已结束活动；如需回归礼包，以独立活动、独立资格处理。
- 新账号、指定大区等资格由活动定义确定，发放端在登录时校验；登录时间不能覆盖活动本身的资格条件。
- 不为离线账号逐个保存“未发放”状态，也不在回归时补建所有错过活动的邮件。到期和发放资格以服务端真实时间为准，不随游戏时钟暂停。
- 一份活动定义可服务所有符合条件玩家；历史活动定义与发放记录仍需有清理期限。默认活动结束 90 天后，确认活动已关闭、延迟任务与重试均已终结，且无待领有效邮件或其他业务引用，再分批清理。任何延迟发放都须重新校验活动窗口；不能因唯一记录已清理而重发旧活动。

第一版为邮件增加明确的附件策略、业务来源类型/ID、附件领取截止时间、失效时间与物理清理时间；`is_claimed` 继续只表达实际已领取。所有新增附件的发送入口必须显式提供策略和来源，未知业务默认保护并告警。不能从展示类别 `reward` 推断可以过期，也不能把本应受保护的资产混入限时礼包；同一业务同时包含两种来源时分别生成邮件。

到期未领取的赠礼拒绝领取，邮件显示“附件已过期”并移除待领取标记；7 天说明期后从收件箱和未读统计移除，再由后台分批物理删除。到期不自动领取，不补发，也不把已过期赠礼转存为无期限资产。领取与过期清理必须通过同一事务锁定和状态复核，避免临界时刻重复入账。

受保护资产不能为满足邮箱条数上限而丢弃，也不自动发到当前城市。当前领取流程包含兵种资格检查、资源与部队入账，清理任务不能绕开这些规则。限时赠礼包含兵种时，要在发放前确认目标玩家能够正常领取，或使用无需兵种解锁的福利；不能发出注定无法在有效期内领取的奖励。

受保护邮件仍可能增长，应按来源统计未领取数量、总量和最老年龄，并限制重复业务邮件的产生：系统奖励有唯一发放来源，重试不能重复生成奖励；同一事件向同一收件人的重复通知可合并，但不同事件、不同资产不能随意合并。

如果这部分以后成为主要容量来源，再拆分独立的待领取附件账本，使通知正文可以过期、领取权利仍保留。第一版不为少量邮件提前引入新的资产结算体系。长期离线本身不授权清除受保护资产；账号注销、删号应按独立账号生命周期规则处理。

### 8.2 演习底层数据

个人演习报告过期后，还需处理 `pvp_practice_sessions`、`pvp_round_orders`、`pvp_round_results` 和终结票据，否则删除报告并不能释放大部分逐回合数据。

- 仅处理已经终结、结算完成且不再有保留报告引用的会话；双方仍有任一保留报告时不得删会话和回合详情。
- 先处理玩家状态中的 `lastSessionId` 等历史引用；保留必要结果摘要，或将其迁移为最后结果摘要后清空会话引用。不能只检查 `activeSessionId`。
- 正在匹配、确认、加载、倒计时、交战或故障恢复的会话、票据、指令不进入保留清理。
- 清理顺序及外键依赖在实施前确认；删除底层记录不得触发重新结算或改变既有积分。

### 8.3 真实战斗凭证

`battle_settlements` 的唯一来源凭证用于防止历史战斗再次发放战果，且当前快照仍参与重复请求处理。它不属于可展示战报的保留对象，第一版保持原有记录，不随报告删除或日志过期裁剪。

后续如需压缩结算快照，须单独证明重复请求、俘虏、资源和兵力处理仍幂等，再设计最小凭证长期保存；不能直接对该表套用 30 天清理规则。

## 9. 监控和发布顺序

按类别记录：候选数、裁剪/删除数、保护跳过数、处理耗时、失败数、最老未处理到期记录、记录总量及增长趋势。附件额外按来源统计限时赠礼发放/领取/失效数、受保护资产积压和未知来源数量。异常长时间积压或内存键数接近上限时告警。

InnoDB 删除记录后，空间通常供后续写入复用，并不保证 `.ibd` 文件立即缩小。不要为了追求文件马上变小，每天自动运行 `OPTIMIZE TABLE`；磁盘容量、备份与 binlog 保留应单独核对。

建议分四步交付：

1. 修正数据库分页、列表/详情按需读取、全部已读批量更新和内存淘汰；这一阶段不依赖任何历史删除。
2. 增加真实时间及期限字段、附件来源与保护策略、限时赠礼发放规则、战报摘要、限额收藏、分享期限和过期提示；新旧接口兼容，完成旧数据安全回填。
3. 维护任务运行至少 7 天的统计模式，输出预计清理量、受保护邮件量、无法生成摘要的记录及演习关联情况，核对备份可恢复性。
4. 启用有界详情裁剪及删除，先少量处理并检查指标，再按既定预算持续运行。历史积压不在第一次启动时一次性处理。

数据库变更采用新的 Flyway 迁移，实施时再确认下一个版本号；不修改已应用的迁移。读取已切换至摘要后仍保留详情兼容读取，直到灰度与观察期完成。关闭清理开关只能阻止后续物理操作，不能恢复已经清理的内容。

## 10. 验收重点

| 场景 | 预期 |
| --- | --- |
| 玩家累计十万份战报，打开列表 | 数据库只读取一页摘要，不加载十万份详情 |
| 浏览列表时收到新战报、翻下一页 | 游标稳定、无重复，且不能跨账号读取 |
| 战报详情 30 天到期、摘要未到期 | 战果摘要仍准确可见，详情明确提示过期 |
| 旧战报需要日志恢复兵力 | 完成摘要验证后才裁剪；失败记录跳过并可追踪 |
| 收藏和后台裁剪同时发生 | 事务复核决定唯一结果，不出现收藏成功却丢详情 |
| 购买、退还等受保护附件超过 60 天未领 | 邮件和领取资格仍在，监控报告积压 |
| 玩家多年不登录，期间开展多次节日活动 | 不预生成个人赠礼邮件；回归后不补建已经结束活动的邮件 |
| 活动期重复登录、请求重试或手动删除赠礼邮件 | 同账号同大区同活动不重复发放 |
| 节日赠礼未读且超过领取期限 | 立即禁止领取并提示过期，7 天后从列表和未读统计移除，不再按未读保留 60 天 |
| 赠礼领取在截止时间前后与清理同时发生 | 持锁后按服务端真实时间复核；过期拒绝，成功入账最多一次 |
| 活动结束后到达延迟发放任务，或旧发放记录已清理 | 重新校验活动已关闭，不能重新生成过期活动奖励 |
| 旧邮件只标为 reward，缺少可信业务来源 | 不推断为节日礼包，不自动作废未领附件 |
| 一封旧邮件今天才领取附件 | 从满足处理完成条件之时开始新的 30 天保留期 |
| 有效中的城市劝降/移交邮件 | 清理跳过，业务仍能正常继续 |
| 清空自己的私聊、随后自动过期 | 清空只影响本人；全局到期后双方均不再读取该消息，未读正确更新 |
| 分享过期或主体详情已过期 | 链接返回明确过期状态，不泄漏详情或放宽原权限 |
| 演习报告被一方清理、另一方仍保留 | 底层会话和回合数据继续保留 |
| 限流窗口重置和淘汰同时发生 | 不重置仍有效额度，不放宽原有每日/频次限制 |
| 停服或游戏时间落后于真实时间 | 生命周期使用真实时间元数据，旧记录遵循过渡期，不混减时间轴 |
| 清理崩溃、数据库短暂不可用或多实例运行 | 已提交批次保留，未完成批次可恢复，不与战斗调度抢占线程 |
| 可展示战报被删除后重试旧结算 | 唯一结算凭证仍在，不重复发资源、部队或俘虏 |
