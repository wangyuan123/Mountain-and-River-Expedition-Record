## 1. 目标与讨论结论

让派驻盟友城市的部队完整参与防守，并保留各自随队军官的战斗价值。城主统一指挥，本城与驻军在同一场战斗中协同作战，各编队分别计算属性、技能、贡献和战损。

### 1.1 用户明确提出的规则

1. 开战时符合驻防条件、已经驻扎在目标城的驻军全部参战。
2. 本城与驻军同场作战，不为每支驻军另开一场战斗。
3. 相同兵种也保留本城与各支驻军的来源，分别按各自军官加成计算。
4. 城市科技等公共配置使用被防守城市的配置，驻军不带入来源城的科技。
5. 战斗日志分别记录本城和驻军的行动、伤害，能够看清团友的贡献。
6. 驻防期间的驻军粮耗由被驻军城市承担，从该城市粮食库存扣除。

### 1.2 上轮解释中提出的建议

1. 同兵种共用城主的行动与集火指令；同步进入机动阶段，各自按有效速度移动。
2. 同兵种、相同行动条件的编队组成协同行动批次，分别计算伤害，再统一应用结果。
3. 日志展示顺序不构成新的行动时机，不因拆成多支编队额外插入敌方攻击或反击。
4. 不增加“本城与驻军轮流先打”的机制，不固定本城先打、驻军补刀。
5. 不同兵种继续遵循原有射程、速度、目标领域、距离和胜负规则。

后续章节把上述建议细化为可实施的规则。涉及现有规则尚不能直接确定的部分列在第13节，待评审时确认。

## 2. 当前实现与目标差异

当前基线以工作区源码和现有文档为准；本节是设计前的现状记录，不是本次修复结果。

| 事项 | 当前基线 | 目标方案 |
| --- | --- | --- |
| 参战数量 | 本城和驻军合并后受城主迎战预设及上限约束 | 本城按自身迎战规则选兵，符合条件的驻军全量追加 |
| 同兵种分组 | 相同兵种与配装可以合并，不同配装保留不同组 | 即使兵种、配装相同，也保留各驻防编队身份 |

## 3. 全量参战与参战边界

### 3.1 驻军全量参战

开战快照应纳入所有同时满足下列条件的驻军：

- 已经抵达目标城市，驻防状态有效，拥有正数量存活部队。
- 驻防目标、接收城主和同军团支援权限在开战时有效。
- 没有在开战锁定前进入返程或完成遣返。
- 不属于其他已锁定战斗中不能重复使用的兵力。

满足条件的驻军不再受城主迎战数量、迎战兵种勾选或本城带兵上限二次裁剪。每支驻军在出发时仍必须满足派兵方既有单队带兵上限、库存、路线、军官占用和油耗校验。

2026-10-30更新：本城全部可战部队与有效驻军均全量参战，不使用历史迎战数量预设或出征带兵上限，不在合并前后裁剪任何有效参战兵力。

### 3.2 开战后到达与并发

- 以战斗会话成功创建时的驻防快照确定参战名单。
- 战斗期间抵达的驻军不加入已经开始的战斗，也不承担该场战损；可参加下一场符合条件的战斗。
- 同一支兵力不能同时进入两场战斗。后续来袭按现有城市战斗排队或互斥规则处理，不新增同兵力多场参战入口。
- 参战编队交战期间不能撤回、遣返或转移；离线、切城和刷新不改变锁定状态。该限制按实际参战来源ID判断；迟到、未参战驻军没有本场战损锁，推荐允许其撤回或遣返，避免其不能防守却被迫持续耗粮。
- 全量参战需要通过容量和性能验收，不因服务器处理压力静默丢弃驻军。

攻击城主时仍需防止同一实体兵力被普通守城与独立侦察拦截同时扣减；排队请求在取得锁后重读存活兵力、城权、战争和接收权限。正常锁内竞争的抵达，以实际状态转换的游戏时间和事件顺序确定先后，不按客户端到达通知的先后判断参战。

“驻军全部参战”是全部有效且已到达的驻军，不包括在途、返程、权限失效和迟到编队。侦察拦截的兵种领域限制另见第11节。

## 4. 编队身份与加成归属

### 4.1 独立计算的最小单位

建议采用“来源编队 × 基础兵种 × 兵种配装”作为战斗分组。来源编队区分本城和每一支驻防行军，不只按玩家区分。

例如本城1万重坦、甲玩家驻军1万重坦、乙玩家驻军1万重坦，应形成三个来源组。同一玩家派出两支配有不同军官的驻军，也必须形成不同来源组。无随队军官的驻军仍参战，其个人军官层取无加成，不能借用城主或其他驻军将领。

数据可以为性能做内部聚合，但必须能够无损还原各来源的独立属性、存活数量、伤害和损失，不能把聚合结果当作统一军官编队。

### 4.2 加成来源表

| 配置层 | 本城参战编队 | 驻军编队 |
| --- | --- | --- |
| 基础兵种属性与克制 | 当前兵种规则 | 当前兵种规则 |
| 战斗科技 | 守城方科技快照 | 同一份守城方科技快照 |
| 城市公共战斗配置 | 被攻击城市的有效配置 | 同一份被攻击城市配置 |
| 司令部司令官常驻四属性 | 被攻击城市司令官 | 被攻击城市司令官，不叠加来源城司令官 |
| 带兵将领属性 | 本城实际守城将领 | 该支驻军随队将领 |
| 将领穿戴装备、套装共鸣 | 本城将领的有效属性 | 该支驻军将领的有效属性 |
| 带兵将领技能 | 仅作用于本城所属编队，按技能规则生效 | 仅作用于对应驻防编队，按技能规则生效 |
| 兵种装备 | 城主的兵种配装快照 | 建议保留派兵人的兵种配装快照，沿用现有来源差异 |
| 伤兵回收 | 城主医疗科技与本城参战将领 | 原派兵人医疗科技与该驻军随队将领 |
| 驻城／驻防粮耗 | 从本城粮食库存扣除 | 驻防期间从被驻军城市粮食库存扣除，不向原派兵城市重复扣粮 |
| 工事、城墙 | 被攻击城市原有归属及规则 | 不因驻军军官数量增加而重复获得加成 |

“科技跟随本城”在本文指场上战斗属性；战后伤兵回收仍使用资产所有方的既有规则，避免驻军归属和回收权益发生隐性变化。兵种装备不等于将领装备，推荐保留现有来源归属，最终选择列入第13节。

### 4.3 计算原则

对每个来源组分别构造战斗上下文：

```text
来源组有效属性
  = 现有兵种与配装计算
  → 守城方战斗科技
  → 被攻击城市公共常驻加成
  → 本来源随队／守城将领的属性与技能
  → 当次攻击目标、领域、距离及克制计算
```

以上表示配置来源和计算边界，不是要求把所有属性使用同一乘法公式。攻击、防御、生命、速度、借鉴和临时效果继续复用现有各项公式及组合顺序，不重复计入装备或共鸣。

技能沿用每隔三回合生效的既有节奏。周期起点的推荐方案改为每个来源编队独立记录，详见第4.4节；初版“全场共用E”保留为待比较的备选，不再作为默认推荐。司令官技能仍不参与。

“全军冲锋”等技能名称中的“全军”在此解释为该带兵将领所属编队，不自动扩散给所有驻军；不因派驻多个同技能军官使整个守方反复叠加。破甲、压制、反击、借鉴等涉及敌方的效果，也必须保留施加来源与作用对象，不能写入全守方共享的临时上下文。

### 4.4 每支编队的独立技能周期（推荐，实施前确认）

每个来源编队记录自己的首次实际交战回合 `E_source`。该编队的周期性将领属性与技能在 `E_source、E_source+3、E_source+6……` 生效，不被其他来源先交火而提前消耗；具体起点判定与适用技能清单需在实施前确认。

- “来源编队”对应本城守城编队或某一支驻防行军。同一编队内多个兵种／配装组共用该随队军官的周期；拆分展示组不生成新的周期。
- 推荐将该来源第一次实际执行合法主动攻击或被实际分配合法攻击份额所在回合记为起点，并在该事件伤害计算前确定窗口。不能以最终伤害／击杀是否大于0判定是否接战，否则会与防御技能产生循环依赖；单纯移动、射程外命令、只有候选目标但未实际攻击或其他来源交火不启动周期。反击沿用其受击时已经启动的周期，不另开起点。
- 已开始交战后，脱离射程、待命、切换目标、部分兵种阵亡、刷新和切换视角不重置周期。
- 例如援军甲第3回合首次交火，其窗口为3、6、9……；援军乙仍在推进，到第5回合首次交火，则其窗口为5、8、11……，不会因甲先开火而错过自己的首次窗口。
- 同一个协同行动批次允许不同来源的技能激活状态不同，分别取各自上下文计算，再按批次统一提交。统一指挥、同步机动与技能时钟独立并不矛盾。
- 首次交火若在机动后确定，闪电突击不能追溯增加已经完成的位移；首次激活是否影响当回合先手，按第4.5节选择并冻结一种版本，不能笼统以“沿用原规则”替代定义。
- 全场首次交战回合可继续保存，用于战斗过程和兼容；不能用它覆盖各来源周期。城市司令官常驻加成不变为周期技能。

审阅补充：独立技能周期的来源粒度是整支驻防行军，并非每个兵种。若同一支援军同时带远程和近战，远程先交火仍会启动整队周期；本设计的“近战不被远程提前消耗”仅指不同来源编队。若希望同一编队内各兵种也独立起算，属于另一种机制，须重新评估技能次数和拆队收益，不能在实现中默认扩大。

备选为全场共用 `E`：实现较简单，但存在远程先开火、近战尚未接触便消耗周期窗口的问题。本文推荐独立周期，并将最终选型保留在第13节，不能把两个起点同时用于同一场新规则战斗。

### 4.5 首次交战与速度技能的阶段顺序（审阅补充，待定稿）

“先有首次交战才激活闪电突击”与“闪电突击速度决定谁先交战”可能互为前提。第4.4节的说明尚不足以消除排序循环，实施前必须选择确定的阶段规则，不能在遍历到某来源时反复重排已执行队列。

推荐方案：回合开始使用已持久化的来源周期判断机动技能；完成同步机动后，按此时已经确定的有效射程、速度生成并固定本回合交火优先级。尚未交战的来源在第一笔实际、合法的主动攻击或受击事件开始时记录 `E_source`，先确定该事件的攻防技能窗口，再计算伤害；这一新激活不追溯位移，也不重排本回合已经固定的先手。后续技能窗口正常参与机动和先手。

该方案与当前全场首次交战后即时启用闪电突击先手的规则有区别，应作为新战斗版本的明确选项确认。如选择机动后预扫描首次接战再统一排序，则必须定义被更早击杀、临时失去目标或零伤害事件的起点，证明候选目标变化不会导致结果依赖遍历顺序。两套算法不能混用。

## 5. 统一指挥与同步机动

### 5.1 谁来指挥

城主负责本城与全部参战驻军的守城指令。派兵人查看自己的驻军状态和贡献，首版不另开多人同时下令入口。离线或超时使用守城方既有默认指令。

同一个基础兵种共用行动与集火命令。城主选择“重坦前进，集火敌方步兵”时，本城重坦与各支驻军重坦一起接收该命令；其他兵种不随之改变。

指令表达的是意图。各组仍独立检查射程、距离、存活目标和行动条件。某组尚未进入射程时，不因另一组已经能开火而获得越距攻击；指定目标失效时沿用既有索敌及回退规则。

### 5.2 同步的含义

同步表示同回合、同阶段读取阶段开始快照并执行，不等于所有部队移动距离和伤害相同。

1. 回合开始冻结有效指令和存活数量。
2. 所有来源组使用同一份机动前坐标规划移动。
3. 各组根据自己的有效速度计算步长，沿用接触、边界和不能越过敌军的规则。
4. 全部移动规划完成后统一更新坐标，再进入交火。

如果驻军军官技能使其坦克更快，该组可以前进得更远；这仍然是与本城坦克在同一个机动阶段执行“前进”。日志分行不能让后一行读取前一行已经修改过的敌方位置来获得额外移动。

## 6. 协同行动批次与伤害结算

### 6.1 保留原有先手规则

机动完成后，不同兵种继续按有效射程、当回合有效速度等规则取得交火机会；首次技能激活影响速度的阶段边界以第4.5节最终版本为准。同射程同速度的攻守先手沿用现有回合轮换规则；这是敌我双方的先手规则，不是本城和驻军之间的轮换。

早期曾建议“本城与援军在相同条件下稳定轮换先后”，后续讨论改为同兵种、同条件协同行动并统一结算，因此不再采用该同侧轮换建议。其防止本城固定先杀、驻军固定补刀的目标，改由批次开始快照与统一提交保证。日志本城排在前面只为便于阅读，不代表先攻击。

本方案不把整场所有攻击改为同时结算，也不取消不同兵种的战术差异。

### 6.2 同兵种协同

建议把同侧、同基础兵种、相同行动指令、相同集火意图且相同交火优先级的来源组组成一个协同行动批次。来源身份、将领和攻击防御差异不要求合并。

一个批次内：

1. 读取统一的批次开始快照，包括兵力、位置、来源技能状态和攻击预算；选择当前同一目标组，确定合法参攻、受击来源。
2. 对当前目标进行一轮协同攻击，各来源按自己的属性、可分配攻击预算、距离和目标防御独立计算。
3. 统一应用这一轮的伤害和击杀，扣除已经使用的攻击预算并记录贡献，不在此之前按来源日志逐行修改目标。
4. 由受击后仍存活、符合射程与技能条件的来源触发有额度的反击，统一提交相应损失；反击不能再次触发反击。
5. 尚有合法余伤预算且仍存活的攻击来源再共同选择下一目标组，重新检查领域、射程和属性，重复上述步骤；已被反击全灭的来源不再参与。

批次的第一次协同攻击使用同一个攻击前快照；后续余伤子步骤使用前一子步骤及反击提交后的存活状态，不能整批始终锁用开头兵力。后续预算如何随反击损失减少须保留现有计算口径并补充预期测试。此前批次发生的真实伤亡同样生效。

审阅明确：统一提交只针对当前目标的一轮协同攻击，不是先完成对全部目标的余伤链再反击。后一种顺序会让本应被反击全灭的部队继续消灭后续目标，改变既有反击作用。

如果同兵种因为配装或当回合速度技能形成不同交火优先级，本文推荐保留其有效射程、速度差异，分别进入对应批次；它们仍共用指令并同步机动。是否改为同兵种无条件同批，作为明确的评审项保留，不在实现时自行替玩家决定。

### 6.3 防止拆队改变结果

协同不是把每个来源都当成一支享有完整额外攻击机会的新兵种。必须满足以下约束：

- 每支编队只拥有其真实兵力对应的攻击预算；不能因来源数量增加重置火力密度或获得多次全额攻击。
- 对同目标的集火采用共同分配过程，避免第一条日志先杀死目标，使后续来源无意义浪费攻击。
- 延续原有余伤转移规则，每次切换目标重新检查领域、距离和克制，不能把未用完预算直接当作通用固定伤害。
- 不重复使用已经消耗的攻击预算；不能同时把对目标的过量伤害记为有效伤害，又把同一部分用于攻击下一目标。
- 击杀取整或随机舍入应先在当前目标的等价组层统一结算，再归属来源；不能每个来源独立向上取整、各保底击杀一人或增加独立抽样机会。是否跨行动、跨回合保留不足一单位生命的伤害余量，属于单独的基础战斗机制选择，不能从“目标侧统一”推导出默认新增持续残血。
- 属性、命令、位置完全相同，且不存在具有真实独立范围的技能差异时，只改变来源分组不应改变总伤害和战斗结果。

来源贡献区分“计算伤害”和“实际有效伤害”。有效伤害不超过目标可承受生命；需要把整数击杀归属到来源时，推荐按有效伤害贡献分配并统一处理余数。归属展示不能反向改变真实结算。

推荐受击分配细则：先按现有同兵种优先／最近目标规则确定目标兵种及可达前排距离层，只在当前可攻击的同距离目标组中，按存活单位数分配攻击预算；各组再使用自己的防御、生命及技能。后排、超射程或不可攻击领域不得获得分摊份额。前排全灭后的余量进入下一轮选敌，不预先分到尚不可达后排。该方案仍需在第13节定稿。

当前引擎在不足整单位击杀时使用概率舍入。新方案推荐保留该概率机制，按同目标等价组聚合后抽样；若改成确定性累积伤害，须明确版本与平衡影响。随机源应由战斗种子、回合、行动及目标等价组等稳定键确定，不能使用日志行序或单纯来源组数量作为抽样顺序。只有同快照、同指令、同规则版本、同随机种子才要求复现同一结果。

贡献展示采用可加总的最小伤害精度分配展示余数，避免各行四舍五入后合计与总览不同。伤害贡献与整数击杀分开保存，不能把显示的伤害反推击杀数；概率舍入可能使二者不完全对应。

### 6.4 反击与受击

敌军不能因为日志从一行变成三行，获得三次原本只对应一次行动的额外反击。建议一次协同行动批次视为一个对应的触发机会，再按现有技能条件计算。

每个实际受击来源单独记录反击触发状态与已用次数，不能共用全守方计数，也不能把敌方每个来源、每条日志或每段余伤都视为新的无限反击机会。反击必须有明确、有限的额度；相同批次的同一次受击事件要去重。最新推荐为第16.3节的“来源编队×受击基础兵种×技能生效回合”额度，单纯拆分配装组或日志不得刷新额度。

反击由实际拥有该技能的受击来源触发，使用该来源的军官与守城公共配置；不能借用同城其他军官的反击技能。建议以该受击来源本次实际承受的攻击份额作为反击对象权重，只向实际攻击过它、仍存活且在其反击射程与攻击领域内的来源分配反击预算，各目标再使用自己的防御和生命结算。不能用整批伤害贡献让未攻击该来源或射程外的部队代受反击；不可用目标对应份额不额外增加反击预算。具体分配和额度仍见第13节。

早期推荐为每个来源在其技能生效回合最多反击一次，存在小规模步兵受击先耗尽整队额度、导致坦克无法反击的问题。最新推荐按第16.3节细化到每来源每个受击基础兵种各一次；同兵种不同配装共享额度。此为新规则建议，并非当前引擎已有上限，仍需验证混编和多兵种接战平衡；不能对多个反击目标重复生成满额预算。

多个来源对同一轮协同攻击反击时，建议共同读取这一轮主动伤害提交后的快照，分别计算后统一提交反击结果，再进入余伤子步骤，不能靠反击日志顺序改变其他合法反击的目标或存活基数。已经被主动攻击全歼的来源不反击，反击不触发反击链。

被敌军攻击时，目标也必须能够区分不同来源的同兵种，使用实际受击组的防御、生命和技能。建议玩家的“集火某兵种”仍为兵种层意图；对该兵种多个可攻击来源组按公开、稳定的分配规则分摊攻击预算。不可按来源行军ID决定先杀本城或固定牺牲某支驻军。

如果目标组的防御不同，分配的是攻击预算或攻击份额，再逐组计算伤害；不能先用一个统一防御算总伤害，之后按人数分摊。

## 7. 战斗日志与界面信息

### 7.1 日志结构

回合下先标注协同批次，再分行展示来源。行序可固定为本城、各驻军，便于阅读，但必须标明“同批次结算”，不能让阅读顺序表现为实际先后。

每个来源使用两行格式：第一行标明本城／援军、所属玩家、参战将领、兵种及行动前数量；第二行记录该来源的实际行动和伤害。标准展示示例如下：

```text
第 N 回合 · 重型坦克协同行动 · 同批次结算

【本城·守将张某】重型坦克 ×10000
前进300，攻击敌方步兵，造成……伤害。

【援军·玩家A·将领李某】重型坦克 ×10000
前进300，攻击敌方步兵，造成……伤害。

本批次合计：有效伤害〔合计〕，敌方损失〔合计〕。
```

字段模板与展示规则：

- 本城标题：`【本城·守将{将领名}】{兵种全称} ×{行动前数量}`。
- 援军标题：`【援军·{派兵人公开统帅名}·将领{将领名}】{兵种全称} ×{行动前数量}`；每支驻防编队分别展示。
- 本城未任命参战守将时使用`【本城·无守将】`；援军未带将领时使用`【援军·{派兵人公开统帅名}·无随队将领】`，不能填入城主或其他编队将领。
- 将领名读取该来源的开战快照，不以战后改任或改名覆盖；界面名称与内部归属ID分开保存。
- 标题数量使用本次行动批次开始时的存活参战数量，不能始终显示开战初始数量。
- 第二行按实际结果显示前进、后退或待命、目标和伤害；“造成……伤害”默认展示实际有效伤害，计算伤害及过量部分可在明细中区分。未开火时写明原因。
- 反击、余伤转移和技能事件同样携带对应来源标题，不能把多支编队的独立军官效果写成一条无来源的全守方日志。
- 同批次各条日志连续展示，并保留“同批次结算”标记；展示顺序不改变机动、攻击、反击或击杀归属。

示例中的1万坦克来自讨论场景，“前进300”、人物名称及伤害占位仅用于说明格式，不是实际测试结果、固定移动距离或新的伤害参数。两支编队速度不同时，应各自展示实际移动距离，不能为了版式一致写成相同数值。

日志验收应覆盖有将／无将、多支同玩家援军、行动后兵力变化和历史快照；确认标题来源、将领、数量与伤害逐条对应，日志汇总与实际结算一致。

日志应保留来源组、行动批次、兵种、行动前数量、实际移动、目标、计算伤害、有效伤害、损失、余伤转移、技能触发及原因字段。未开火时显示未开火原因，不生成虚假零伤害攻击；不同速度、射程或位置导致的行动差异应可解释。

展示名称使用公开统帅名与编队标识，不展示登录账号。历史日志按原规则展示，不用新模板推断不存在的来源或军官。

### 7.2 指挥面板与战报

- 同兵种保留统一指挥入口，展开后可查看本城与各驻军数量、随队军官及生效加成来源。
- 显示“本城全部可战兵力及已到达的有效驻军全量参战，不受带兵上限限制”，说明迟到驻军不加入本场。
- 战报展示防守总览及来源明细：初始数量、幸存、损失、伤兵、有效伤害和参战军官快照。
- 视图切换、攻守视角交换和刷新均引用同一组来源ID、批次ID和快照，不以名称或页面行序关联数据。
- 可按来源或兵种筛选日志；汇总必须与明细守恒。展开明细不能改变城主已经下达的命令。

详细属性和来源可见性继续按城主、派兵人及对手现有权限控制。公开排行榜、玩家资料和第三方分享不能因此获得未侦察授权的驻军情报、实时主城坐标或军官配置；对手战报的新增明细字段应单独审查其公开范围。

审阅补充：现有分享凭证可读取完整战斗战报，不能只改战场界面后让分享接口直接透传新的内部快照。新增来源军官、原城市标识、内部ID、配置层和坐标需在普通读取、分享读取、WebSocket和导出等服务端响应中统一裁剪。分享展示的是生成时允许公开的历史战斗信息，不查询当前主城位置、驻军或装备；未定义的新敏感字段默认不公开。

标题数量是交火批次开始的存活数量，移动事件则发生在此前的同步机动阶段；若期间已受击，不能把该标题数量误当作实际移动时数量。结构化事件分别保存移动前数量和攻击前数量，合并展示时必要则注明“机动时×N，交火时×M”；保持用户指定的来源标题与两行基本格式。

战报提供防守总览及按来源编队展开的贡献表，同一玩家的不同驻防行军不能只合成一行。同一来源可继续展开兵种／配装明细。

“参战人数”统一按游戏兵力单位数统计，坦克、飞机、舰船等不换算为现实乘员人数。战损包含入营伤兵，不能再把伤兵加到战损上重复计损；各行初始数量等于幸存与战损之和。

有效伤害采用引擎当次计算伤害经目标剩余可承受生命封顶后的 `appliedDamage`，不把过量伤害记为贡献。保留概率击杀机制时，这不是新增的跨回合连续扣血，不按整数击杀数乘单位生命重新生成贡献；士兵、工事和城墙伤害分项，展示总值时注明口径。可展示伤害占比，其分母为本场防守方相同口径的有效伤害合计；总值为零时显示“—”，不能出现除零结果。贡献仅用于复盘，不新增奖励、排名或击杀收益。

城主查看本城及收到的全部驻军贡献；派兵人至少能复查自己各支驻军的参战、伤害、战损和伤兵。对其他来源的细节、对手视角及分享范围仍按第7.2节和第13节的情报权限要求处理。

## 8. 战损、伤兵、军官与城市归属

### 8.1 逐来源结算

战后按每个来源组的实际初始与幸存兵力计算损失，扣减对应本城库存或驻防行军。损失不能重新按全守方初始人数分摊，否则会抵消各军官防御和生命差异。

每来源、每兵种均应满足：

```text
开战参战数量 = 战后幸存数量 + 本场损失数量
本场损失数量 = 依现有规则入营的伤兵 + 其余损失
全部来源的各项合计 = 战报防守方对应总计
```

本城未参战部队、战斗期间新增部队和迟到驻军不扣该场损失。不得用开战时的库存全量覆盖战后实时库存。

### 8.2 资产与军官

- 驻军幸存部队仍属于原派兵人和原驻防行军，不转为城主可自由出征的库存。
- 伤兵进入各自原派兵城市的伤兵营，批次期限、费用和回收比例沿用现有规则。
- 战后驻军继续驻防或按撤回、遣返、权限失效规则返程；返程不重复返还伤兵或阵亡部队。
- 城市被接管时，先完成驻军战损结算，外来幸存驻军再按既有规则返回，不随被接管城市转移所有权。
- 本方案只改变参战和计算方式，不自动扩大军官俘虏范围。驻军全灭及随队将领处理先沿用既有驻防规则；驻军将领是否可被俘属于独立设计项。
- 退团、换团、换装、加点、军官改任等操作不得追溯改变已开战编队。开战前权限失效与开战后权限变化分别按快照边界处理。

### 8.3 原派兵城市失守与结算时点（审阅补充）

原城失守清理外派行军、军官的既有流程，与“已参战编队锁定到终局”存在冲突。推荐活动战斗中的来源行军及军官先保留为不可再使用的结算引用，待该场终局扣损、生成贡献和伤兵记录后再做失守清理；不能中途删除参战实体，导致无法结算或重复返兵。未参战外派资产按既有失守规则处理。

原城仍属于原玩家时照常返还；已不属于原玩家时，幸存者及伤兵的去向必须按原玩家的重建／重归属规则确定，不能凭历史城市槽向占领者库存入兵。具体安置城市和军官清理优先级列为第13节实施前必定事项。

伤兵回收现有规则在战斗结束时采样医疗技术与随队急救技能，第9.1节原先把回收配置列入开战冻结，二者不一致。本文推荐保留既有终局采样口径：开战冻结用于战场攻防的属性与技能；终局在军官转籍／释放、城权清理之前，按各来源原玩家身份采样医疗与急救并保存实际回收率，之后不重算。无军官仍不借用其他编队，原城失守需保留完成采样所需引用。若选择连医疗回收也在开战冻结，应同步变更伤兵设计及规则版本，不能把两种时点都写成“沿用”。

## 9. 快照、数据与兼容建议

### 9.1 开战快照

建议在当前战斗会话中增加可版本化的来源组快照，而不是创建多份相互独立的战斗。字段名为设计建议，后续实现需结合现有结构确定。

| 字段类别 | 建议内容 |
| --- | --- |
| 规则与时间 | 规则版本、游戏时间开战采样、全场首次交战回合、最大回合数、战斗随机种子及稳定事件键版本 |
| 来源 | 不透明且稳定的来源组ID、本城／驻军、原玩家、原城市、原驻防行军ID |
| 兵力 | 基础兵种、配装组、初始与当前数量、位置、剩余伤害状态 |
| 军官 | 实际参战军官身份、公开名称、含装备／共鸣的有效属性、技能快照 |
| 来源战斗时钟 | 各来源首次交战回合E_source、当回合技能窗口、反击已用次数及规则额度 |
| 公共配置 | 守城科技、被攻击城市配置、守城司令官快照 |
| 来源专属配置 | 开战兵种装备及其归属；伤兵回收的原玩家、军官和城市引用（具体回收率按终局时点另存） |
| 过程与结果 | 指令、批次、目标、攻击预算使用、贡献、损失与结算状态 |
| 终局医疗记录 | 终局采样时间、来源医疗等级／急救等级、最终回收率、入营数量与实际归属城市 |
| 粮耗分段记录 | 稳定接收城市与城权世代、来源驻防起止、兵力变化事件、费率有效区间、计量小数余数与已结算游标 |

战场攻防使用的军官、科技、装备等配置建议在创建战斗时采样，整场沿用。伤兵回收按第8.3节的终局采样单独保存，驻防粮耗按第10.1节的游戏时间分段结算，不把整场粮耗费率也自动冻结为开战值。驻防出发时的库存、运力和军官占用仍按既有行军规则校验；不要求把后续可变战斗配置提前冻结到出发时间。

存储的内部归属字段不等于客户端公开字段。接口应按请求者角色裁剪，避免通过来源ID或快照暴露额外情报。

### 9.2 兼容与发布

- 新战斗使用新规则版本；已有进行中战斗继续按创建时版本完成。
- 缺少来源军官快照的旧战斗、旧战报不回读当前军官来补算。
- 旧战报保持既有伤害、归属和结果，只展示真实保存过的信息。
- 自动、手动、离线超时推进和双方视角必须使用相同规则与结算入口。
- 库存扣减、驻军损失、伤兵与终局记录应在现有事务边界内幂等提交，重复推进或重试不重复扣兵、入营或返还。

发布不能只迁移新战斗：已驻扎的旧援军也会开始由接收城承担新增粮耗，应从明确的规则启用游戏时刻起计费，不追扣启用前时段。旧战斗继续按旧战斗版本结算，粮耗则按驻防计费版本和生效时间分段；迁移游标、城主提示及接收设置的默认值须明确。只有新旧规则的读写与推进路径均受支持时才能保留旧会话，否则应在上线前完成旧会话排空。关联的现行规则文档在将来实现时同步更新，当前继续标示其为已实现旧规则。

## 10. 平衡与性能约束

全部驻军参战会增强集体防守，这是设计目标。首版不额外引入驻军折损、全军增益叠加或新的城市驻军总量上限；如果后续需要限制，作为独立玩法调整评审并公开说明。

### 10.1 驻军粮耗与承担城市（用户已明确）

驻防期间的驻军粮耗由被驻军城市承担，直接从实际接收驻军城市的粮食库存扣除。本城部队粮耗仍由本城承担；各支驻军资产归属不变，但驻防期间不再由原派兵城市承担同一份粮耗。接收城为分城时扣该分城粮食，不能扣城主主城、当前界面选中城市或其他城市库存。

- 承担区间从部队成功抵达并进入驻防状态开始，到撤回、遣返或权限失效后实际退出驻防、开始返程时结束。交战锁定期间仍处于驻防，粮耗继续由该被驻军城市承担。
- 在途和返程的行军消耗继续沿用既有规则。造兵、出发所需往返油耗、驻防粮耗和伤兵治疗分别核算；本次只明确驻防期间粮食消耗的承担方，不把油耗、治疗或其他资源费用一并转给城主，也不新增持续石油维护费。
- 驻防粮耗按各编队实际存活兵力和经过时间累计；同一驻防时段只从被驻军城市扣粮，原派兵城市的外派粮耗统计需排除该时段，防止漏扣或两边重复扣粮。
- 抵达、开战、战后损失、撤回和返程等状态变化需形成连续但不重叠的计费区间。战损后的后续时段按实际幸存数量计费，具体切分时点应与战斗结算模型一致；重复Tick、离线补算或请求重试不重复扣粮。
- 城权变化时先结清原城主驻防阶段的应计粮耗；幸存驻军转返程后停止从该城扣粮，不将原城主阶段的未结粮耗转记给新城主。城权转移、驻防解除与资源结算的事务时序需在实施时明确。
- 随驻军携带并交付给目标城的粮食属于该城正常库存，可用于承担本城及驻军粮耗，不建立额外的专属补给账户；已交付物资不因撤回或返程退还。
- 派遣前及收到驻军的管理页明确提示“驻防期间粮耗由目标城市承担”，展示已配置的粮耗估算、扣粮城市及驻军粮耗合计；长期驻防显示当前速率或实际累计，城主能够查看本城部队与驻军的粮耗分项。
- 优先复用现有兵种粮耗标准，具体费率、扣粮间隔、战损切分及目标城缺粮后的处理仍需核对现有经济规则后确定。承担方和资源种类已经明确为被驻军城市的粮食，不再列为待选事项；本文不虚设费率，也不声称现有代码已经实现。
- 被驻军城市缺粮时，不能静默改向派兵人扣粮，也不能在战斗中静默移除已锁定驻军、降低已冻结属性或免除已发生战损。缺粮提示、限制新接收或战后返程等处置需另定，不能借未定义的即时逃兵规则改变战局。

审阅补充：既有持续粮耗由 `TickService.foodPerHour` 统计所选城市库存兵力，现有支援行军没有因此自动计入目标城维护。粮耗接入应扩展实际计量来源及结算事件，不只是修改显示的承担城市。当前行军燃料接口明确不扣粮食，本设计不新增在途／返程扣粮。

所有驻防时长和结算游标使用 `GameClock` 游戏时间：停服不耗粮，玩家离线而服务器运行仍耗粮；资源计算须由目标城及其稳定归属驱动，不能等待派兵人登录才补算。推荐在抵达、兵力变化、经济减耗配置变化、终局、离驻及城权转移前结清前一时段。战斗中存活兵力应读取权威回合结果而非尚未更新的原始行军数量，避免已经阵亡的兵力继续计粮；不为战斗没有推进的未来回合预先计算阵亡。

缺少精确兵力事件时间的自动战斗必须明确等价时点。离线连续推进应使用同一序列的逻辑回合时间，不能把所有过期回合都记为请求处理时刻，否则在线逐回合与离线补算粮耗会不同。自动结算战斗是否占用实际游戏时长及其计量口径需作为第13节定稿项。

基础粮耗优先复用 `UnitDef.food`，推荐援军与本城部队共同使用接收城市城主的军需补给科技（`log_food`）及被驻城实际市长的军屯自给（`ration`）减耗，并保留原有乘法和下限规则；不累计派兵方相同科技、市长或随队军官的经济减耗。它们属于城市经济配置，不受独立战斗技能周期控制，任命或研发变化仅影响之后的计费区间。此为待确认的减耗来源建议。

同一城市汇总基础单位数和小数粮耗后再结算，保留累计小数余数，不按驻军条数或每次Tick独立四舍五入；频繁刷新、拆队或撤回不应减免费用。兵力与时间乘积使用足够范围的数值类型，取整、欠粮和产粮先后顺序与城市经济共用定义，不能为驻军单开一套相反规则。

推荐缺粮采用与本城一致的耗粮规则，明确粮食扣至0后的提示和是否允许继续接收；当前城市经济扣粮会截断到0，不因此自动实现逃兵或债务。若引入自动遣返、欠粮债务或拒收，必须公开其触发和战斗锁后处理，不能把未支付粮耗称为已扣除，也不能通过重试反复尝试扣同一时段。

### 10.1.1 接收城的粮耗控制（新增建议，待确认）

粮耗由接收城承担后，同军团成员无限派兵可能耗尽城主粮食，仅有事后遣返不足以避免交战时被锁定。推荐每城提供“允许接收驻军”开关，派遣前及抵达时均校验，界面同时展示新增粮耗及城市驻军粮耗分项。默认开关值、旧驻军的启用提示及在途改关后的返程须在上线方案中确定，不默认认定同军团就是同意承担任意粮耗。

关闭接收只影响新进入驻防的部队；现有驻军仍可守城，已交战部队不能借开关逃离战损，现有未参战部队可正常遣返。该开关是接收权限控制，不是新增数量上限，也不能在部队成功驻扎后用它在开战时排除兵力。更细的接收白名单或粮耗预算可后续独立评估。

### 10.2 后续可选的驻防接收容量

如果后续为了平衡限制无限堆驻军，推荐限制城市可接收的驻防容量，并在派遣之前明确展示容量计量单位、已用／剩余容量及本次占用，超额时直接说明原因。容量按兵力还是编队计量、是否预占在途名额及各兵种权重需单独设计，不把本城迎战上限当成隐藏的驻军接收上限。

正式派遣需在服务端原子校验和预占容量，处理多名团友并发派兵；预占在取消、返程或兵力损失时按明确规则释放。若未来因规则变更或异常导致抵达时不能接收，应向双方显示原因并按规则返程，不能先显示驻扎成功，开战时再偷偷排除。

本设计首版仍以全部有效驻军参战为目标；接收容量只记录为后续可选方案，没有在本次文档中设定容量数值或默认启用。

### 10.3 拆队公平与性能

同属性拆队不应凭空增加火力密度、攻击次数、最低击杀、技能触发次数或损失取整收益。真实配置差异带来的结果变化应能够由来源明细解释。

内部计算可以按完全相同的上下文做缓存和聚合，但个人军官效果、技能作用范围和资产归属必须保留。日志使用结构化事件，按需分页或折叠展示，避免编队多时生成不可读或无界增长的单段文本。

兵力加总、伤害和生命累计需验证数值范围，避免大量百万级驻军造成整数溢出。性能验收应包含大量来源组和高兵力场景，记录实际规模与耗时，不能预先声称通过。

## 11. 适用范围

首版覆盖玩家城市防守中的普通进攻、掠夺和征服，自动与逐回合模式保持一致；城墙阶段、胜负条件及回合上限继续沿用各自现有规则。

独立侦察拦截有自己的兵种领域、先手和回合模型。空中侦察仍仅由符合规则的空中拦截兵种应对，地面侦察同理，不能把全量坦克或所有驻军直接投入侦察战。建议后续让实际参战侦察编队同样获得各自军官，但应单独设计和验收，不把普通守城的批次规则直接套入侦察。

野地驻军、自有城市调遣、运输和演习继续遵循现有各自规则；来源城失守的外派清理仅对已锁定参战实体增加第8.3节的结算保护与归属要求。本文提出的概率取整、反击额度和技能起点建议必须按新版本评估，不能默认改变无驻军战斗及其他玩法的结果。是否统一升级普通城市战的技能／反击规则需在实施前明确，避免同一账号仅因有无援军就出现未说明的技能差异。

## 12. 验收场景

以下为后续实现应执行的验收清单，本次仅写文档，尚未执行这些新增场景。

| 编号 | 场景 | 预期 |

| A01 | 本城与驻军合计超过城主出征上限 | 本城及有效驻军全量参战，不按出征上限裁剪 |

| A12 | 等配置部队合并与拆为多来源，排除真实独立技能差异并固定种子 | 在相同目标等价组、规则版本和有效周期下总体结果一致，不重置密度、预算或抽样机会 |
| A13 | 两来源攻击同一即将死亡目标且存在其他目标 | 不重复击杀，余伤按预算与射程规则分配 |
| A14 | 同兵种不同来源防御、生命或反击技能不同 | 按实际受击来源计算，不能事后按总人数摊损 |

## 16. 审阅问题的推荐定稿方案（2026-10-24）

本节原为最终推荐方案；用户随后明确要求严格按设计文档实施，现全部作为首版确定规则。与早期候选存在差异时，以本节为准，不同时采用全场共用技能周期、同侧轮换先手或同兵种无条件同批等旧候选。

### 16.1 技能按来源编队起算，先手每回合固定

1. 一支驻防行军是一个技能来源；本城选出的守军为本城来源。整支行军内所有兵种使用同一名将领、同一个 `E_source`，不按单个兵种另开技能周期。
2. 首次实际执行合法攻击，或首次被分配正的合法攻击份额时，在伤害计算前设置起点；无击杀也算接战。只有候选目标、命令超射程和别的来源开火都不启动周期。
3. 周期固定为 `E_source、E_source+3、E_source+6……`；脱离射程不暂停，换目标、刷新和伤亡不重置。
4. 回合开始应用已知周期技能做同步机动；机动后一次性确定本回合先手，新接战即时启用该事件的攻防技能，但不追溯机动或重排当回合队列。闪电突击从下一次有效窗口起正常影响位移与先手。
5. 普通玩家城市战双方按同一新版本处理，攻方作为其随队将领的一个来源；不根据是否存在援军动态选择技能规则。野地、独立侦察和演习首期不改，差异在新规则说明中明确。

此选择牺牲首次接战窗口即时增加速度先手的旧效果，换取阶段顺序确定；需要在技能说明和战报中写明。独立周期按整支行军而非兵种，保留混编提前开火的战术取舍。

### 16.2 同条件同批攻击，逐目标解决伤害与余伤

保留原有射程、有效速度与敌我同值轮换先手。相同基础兵种、命令、集火意图和优先级的来源同批；射程或有效速度不同可以分批，但仍统一接收城主命令并同步机动。日志排在前面不带来先手。

处理每一目标组时采用固定顺序：`各来源独立计算当前攻击 → 同步提交主动伤害 → 存活受击者合法反击并统一提交 → 存活攻击者继续余伤`。不会因为拆来源多出主动攻击、移动或反击时机。

推荐余伤预算随反击损失缩减：某攻击来源当前未用预算为R，反击前存活N，反击后存活S，则后续可用预算为 `R × S / N`；N为0则预算为0。不得恢复本回合开头的完整预算，保留小数到当前行动结束，不跨回合积累攻击机会。这是相对旧部分伤亡处理需验证的明确新口径。

### 16.3 反击采用“编队×受击兵种”有限额度

推荐每个来源的每个基础兵种，在该来源技能生效回合最多反击一次。该兵种不同配装组共享一次事件额度；实际反击预算由这次受击后存活、具备相应技能且可合法还击的受击组共同提供，不为每个配装组或反击目标各生成一份全额火力。

- 步兵先受击只消耗本编队步兵额度，不消耗重坦额度；同一重坦组被多支敌军攻击，也不会反复满额还击。
- 只有实际受击后存活，且存在相应领域、射程内真实攻击者时才消耗额度。被全歼、未带反击技能或无法还击不生成反击。
- 只指向本次实际攻击过该受击来源的敌军，按其向自己的攻击份额分配反击预算；不能打到其他敌军或射程外对象。
- 多个合法反击来源读取主动伤害后的共同快照，算完统一提交；反击不触发反击。
- 额度归本场稳定来源ID、基础兵种和回合，不归日志、配装别名或请求次数；重试不再使用。真实不同将领的独立额度属于不同军队的优势，纯展示拆组不增加额度。

这一方案优于整支混编军队共用一次：既有上限，又避免一小队先受击就耗掉整名将领其他兵种的全部反击机会。次数以一次作为首版明确推荐，后续平衡应以真实对战数据评估，不能宣称当前已经平衡。

### 16.4 承伤只分配给合法目标，保留概率击杀

优先遵循原同兵种／最近目标选择，目标中同距离、同基础兵种且可攻击的前排来源按存活数量分配攻击预算，各自再算防御、生命及减伤。不让后排或射程外来源分担，也不固定本城先掉兵。前排消灭后重新选敌、重算合法距离。

若目标属性完全相同且位置、周期状态等价，先聚合本子步骤伤害并进行原有概率舍入，再向各来源分配整数损失；属性不同则按各自目标上下文分别计算。固定战斗种子和稳定抽样键，调整日志顺序或纯配装展示拆组不增加抽样。首版不引入跨回合残血系统。有效伤害和整数击杀单独记录，汇总与展示分项一致。

### 16.5 粮耗按目标城实际驻防时段和存活兵力计算

粮食承担方保持为被驻军城市。基础标准复用兵种现有每小时耗粮，减耗采用接收城城主的军需补给科技与该城实际市长军屯自给，按现有组合和下限计算，不叠加派兵方的同类减耗。

计量采用游戏时间；离线继续、停服暂停。在抵达、回合伤亡、减耗配置变化、离驻与城权变更时切分区间，累计小数粮耗到城市结算，不按编队条数分别取整。死去部队不计后续粮耗，原派兵城不承担同一驻防时段的重复费用。

不把战斗回合数乘固定秒数当作账单：手动回合以真实推进的游戏时刻、超时回合以截止时刻入账；自动战斗在其既有生效游戏时刻完成，不虚构额外经过的时间。不同实际时长可以对应不同粮耗，相同事件时间轴的在线与离线处理必须得到相同账目。粮耗结算与城权、库存和下一场战斗启动保持事件时序一致。

### 16.6 缺粮先拒收，现有驻军有序返程

推荐在目标城粮食已经耗尽且产粮不足以支付本城与驻军总粮耗时，触发缺粮处置；预计多久耗尽可提前告警，不能等派兵人上线才处理。

1. 立即提示城主和相关派兵人，拒绝新驻军成功进入驻防；已经在途者抵达时若仍不具备接收条件，按既有合法返程处理。
2. 未参战驻军可立即按公开顺序自动遣返；已参战者完成当前战斗，保持本场属性和应承担战损，不即时消失。
3. 终局在创建下一场排队战斗前，重新结算粮食并执行仍然需要的遣返；不能靠连续来袭让驻军永远锁在免费参战状态。若城主及时补粮并恢复补给，先重评估，未必要返的编队不强制返程。
4. 推荐按各编队当前有效粮耗从高到低、同值按驻防时间从新到旧的固定顺序，整队遣返到剩余粮耗能被产粮覆盖；不拆编队、不删除士兵。本城自身仍入不敷出则遣返全部外来驻军，本城缺粮沿用其原规则。
5. 不自动消耗钻石、不转扣派兵人，不建立无限负粮或事后追债；参战锁定期间短缺只允许延续到本场终局，记录该时段未满足需求，不伪称已付款。解除返程后重新派驻仍需满足接收条件。

此为具体推荐的缺粮政策，新增了自动遣返，需要明确提示并获得方案确认后实施；同一编队不得通过反复状态切换重置已经累计的粮耗余数或漏记驻防区间。

### 16.7 接收设置与旧驻军上线过渡

每城提供“允许接收驻军”开关，新增城市默认关闭；城主主动开启后同军团成员可派驻，无需每队再次审批。出发与抵达均重验，关闭后拒绝新驻防，已有效驻扎部队保留并继续承担粮耗、参战；城主可遣返未参战编队。

旧城市上线时同样将新接收设为关闭，并展示已有驻军及预计粮耗；已经驻扎的部队保留，粮耗只从明确公布的新规则生效游戏时刻起算，不追扣过去。此前在途任务在抵达时执行新的接收条件，未获接收则返程并向双方说明原因。旧战斗继续按旧版本完成，不中途切换技能或伤害规则。

首版只加接收控制，不同时增加驻军数量上限或逐队确认弹窗。未来如启用容量，必须派遣前公开并原子校验，不能开战时偷偷裁兵。

### 16.8 伤兵与原派兵城失守

战场攻防开战冻结，医疗回收保留现有终局采样；按实际参战的原玩家与军官，先取得终局医疗／急救和实际战损，保存回收率及伤兵，再释放、俘虏或清理军官引用，不重新计算旧伤兵。

原派兵城在战斗中失守时，不删除正在参战的来源引用；先完成本场唯一结算，再处理原城失守。幸存部队和伤兵始终归原玩家：原城仍属其所有则照常归原城；否则优先其当前主城／重建主城，必要时选择其仍拥有且符合兵种与合法路线的接收城。幸存者执行合法返程，不因换归属城市瞬间加兵；伤兵按现有入营方式归其合法城市。

若没有合法接收城或返程路线，保留原玩家所有的待安置记录，不再作为目标城驻军参战，也不转入占领者资产或静默删除。该异常状态不能靠一般撤回主动创建，须记录失守原因并提供后续选择合法返城目的地的恢复流程；其间按既有外派资产与原城失守规则管理，不继续向原被驻城计驻防粮耗。异常安置的存储和恢复是实施验收项，不能仅靠一个无去向的行军ID占位。

### 16.9 战报明细、权限和展示

保留用户指定的“本城／援军·玩家·将领”两行格式，并显示同批结算。移动前与攻击前兵力不一致时分别注明。贡献表保存参战、有效伤害、损失、伤兵和幸存，不从最终总战损反推每队贡献。

城主可见本城与驻军的授权战斗明细；派兵人至少可见自己编队。对手只获本次战斗规则允许公开的历史行动、兵力／战损与已公开技能事件，不新增军官完整属性、全部配装、来源城ID或实时主城坐标。分享使用单独的公开字段列表，不直接透传内部快照，页面、读取接口和推送执行同一权限。

### 16.10 首版范围与验证

首版一起完成全量参战、来源军官隔离、协同结算、粮耗与接收／缺粮控制、贡献战报及旧数据过渡。继续保留驻军随队将领装备和派兵方兵种配装；压制、破甲等只进入本次实际来源与目标的计算，不累加成全守方状态。同名借鉴／借甲在当前合法目标兵种的参考来源中按存活兵力加权读取原规则允许的参考属性，沿用技能互斥和借鉴排除项，不复制对手周期技能。

驻防容量、额外援军将领俘虏、侦察军官新模型留作后续独立设计。技能／反击、借鉴多来源、概率拆组公平和缺粮遣返都需真实对战与对照测试，不因方案写成明确推荐就免于平衡验证。A01～A47按最终采用版本补齐固定输入、种子、事件时间和期望结果，再执行回归及规模测试。

上述方案已用于本次代码实施。验收与尚未覆盖的运行环境验证独立记录，不将方案文字本身视为测试通过。


## 17. 实施与兼容口径（2026-10-24）

- `GuildSupportService` 纳入本城全部可战兵力，再全量追加有效驻军，不受出征上限限制；普通城市战按来源行军保留别名，来源将领属性含装备和共鸣。驻军兵种配装沿用出发时快照；普通城市战的来源军官与公共战斗科技在开战时冻结。
- `BattleService.resolveJointRound` 共用一场战斗，按来源起算技能，固定回合先手，同条件协同攻击、逐目标统一伤害、有限反击与幸存者余伤。固定种子使用稳定字符串键，不依赖进程内对象哈希；概率与来源日志顺序解耦。
- `GarrisonFoodService` 与 `GarrisonFoodTimeline` 按游戏时间重放抵达、队列完成、回合伤亡等事件，保留城市小数余额；接收城可处理离线派兵人的到期支援。缺粮按有效粮耗从高到低、同值新驻军优先整队返程，已参战来源等待本场结束后重新评估。
- 原城失守的参战驻军与军官保留至终局，伤兵采用原玩家终局医疗配置，幸存者选择合法原玩家城市真实返程；无合法目的地时保存 `displaced` 待安置状态，军情提供安置入口，Tick 也会重试。城权移交先结清旧账，新城默认拒收。
- 新日志保存来源、批次、移动与交火前数量、有效伤害和实际战损；战报贡献显示部队／工事／城墙伤害，以0.01为显示精度按侧别和类型统一分配尾差。医疗采样保存时间、科技、急救、实际回收率与归属，只向资产原玩家返回；分享采用独立白名单。
- V126 将旧城市的接收设置关闭，保留旧驻军；旧驻军从迁移时已持久化的游戏时刻计粮，不追扣。`joint_defense` 为空的旧会话保留旧引擎，已有战报不从实时军官重算。
- 新普通玩家城市战均采用本版本，包括无援军的城市战；独立侦察、野地、演习保留各自引擎。现行规则已同步到军团支援、战场、司令官、兵种装备、伤兵与接管文档。

## 城市交战期间禁止出征（2026-10-30）

玩家城市正式创建守城战斗会话后，整座被攻击城市禁止发起任何新的出征，包括攻击、侦察、采集、野地进驻、运输、自有城调遣、军团援军派遣和出城拦截。本城未参战部队及战中新增部队同样不能外派。其他城市和已在城外的行军继续沿用既有规则，参战援军继续执行原有战斗锁定规则。

锁定以该实际城市 ID 对应的活动守城战斗会话为准，与宣战、备战、敌军尚在行军或雷达可见性无关。终局结算与战斗会话删除在同一事务完成后自动解锁，不新增独立的持久化锁定标记。后续排队敌军建立下一场会话后再次锁定。

正式出征及快捷入口均在城主账号写锁内读取最新守城会话，与开战、终局串行处理；锁定时返回 HTTP 409、错误码 `CITY_IN_BATTLE`，提示“当前城市正在战斗，暂时无法出征，请等待战斗结束”，不扣兵、不扣资源、不新增行军。状态接口返回当前所选城市的 `cityBattleLocked`，前端锁定期间展示提示并禁止提交，后端仍作最终复核。


## 19. 全员守城规则更新（2026-10-30）

本节覆盖早期保留本城迎战预设／上限的历史方案，其余来源隔离、技能、装备、科技、结算、粮耗、接收和返程规则不变。

- 本城与分城分别以开战时本城全部可战库存参战；百万兵力不受军衔、统帅或动员容量裁剪。卡车、运输机同样参战并承担实际战损，工事另行加入。伤兵、在途和其他城市的兵力不加入。
- 历史迎战数量预设停用，包含零兵力预设；不提供只派部分守军的入口。主动出征的容量与校验保持有效，各支援军从原城出发时同样受派兵城市上限限制。
- 已创建会话保留原快照，不补兵也不追溯变更；新战斗冻结新的全员名单。战中新造、返城与迟到援军从下一场参战，普通战损只扣快照中的实际损失。

- 动员不再复制、切换或恢复守城数量预设，启停只影响新出征容量；行动草稿不因到期丢失。旧数据库字段仅保留兼容，接口兼容语义见 DESIGN.md。
