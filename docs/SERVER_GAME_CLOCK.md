# 停服暂停与恢复

更新于 2026-10-20。本文是[主设计“时间与结算”](DESIGN.md#时间与结算)的统一时间口径，适用于所有大区内游戏活动。相关源码及迁移已实现；本文不代表已部署或已执行生产迁移。

所有游戏活动统一使用持久化游戏时间 `GameClock.now()`。每个大区数据库维护一个 `game_clock` 检查点，每秒先提交检查点，再将时间提供给业务结算。服务器启动后从最后检查点继续，不增加停服期间经过的真实时间。

例如：停服前行军剩余 10 分钟，停服 2 小时，恢复后仍剩余 10 分钟。服务器正常运行而玩家离线时，活动继续。

## 时间定义

- **真实时间**：日历、鉴权和运维使用的墙钟时间，不作为游戏活动推进依据。
- **游戏时间**：仅累计服务器有效运行时长的持久化时间；运行期间以单调时钟计算增量，避免系统墙钟校准导致进度跳变。
- **活动截止时间**：保存于同一游戏时间轴，剩余时长为 `max(0, deadline - GameClock.now())`。停服不修改每条活动的截止时间，也不逐项重排队列。
- **预计真实完成时刻**：`真实当前时间 + 剩余游戏时长`，只表示当前预计值；后续暂停会顺延，不承诺固定日历时刻完成。

## 覆盖范围

- 行军、返程、运输、驻军、野地采集与自动收获。
- 野地及真实玩家战斗、战术回合、宣战准备期和交战期。
- PvP 匹配、确认、回合期限、超时和冷却。
- 建筑升级与拆除、科研队列、造兵、城防、部队装备生产。
- 资源及人口增长、军饷与维护消耗、伤兵保留期。
- 新城建设、护盾、新手保护、加速效果、安抚与军官冷却、晋升考试、劝降答复和城市移交。
- 野地和据点三小时刷新；军校与改名日额度按游戏时间的北京时间自然日重置，停服顺延。

### 周期与自然日

野地／据点刷新保留游戏时间的北京时间 00:00、03:00、06:00、09:00、12:00、15:00、18:00、21:00 边界。调度器每秒检查周期 `floor((gameTime + 28,800,000) / 10,800,000)`，以 `game_schedule` 持久化已处理周期并在事务内加行锁；首次建立基线，不立即刷新。游戏时间冻结时不跨周期，重启不补跑停服期间的真实日历刷新点，也不会重复刷新已处理周期。

军校、改名等每日额度按游戏时间转换到北京时间后的日期判定。此处“北京时间”仅规定游戏日期的 UTC+8 边界；累计停服后，游戏日期和真实日历可以不同。合规开放日历仍按真实日期，不随游戏日期顺延。

## 运行边界

`GameClockRuntime` 在数据库初始化后安装，世界启动修复完成后才推进。正常退出主动释放租约；强制终止也保留最后已提交检查点，未提交的不足一个心跳零头不参与结算。

数据库提交失败时保持旧游戏时间，失败间隔不在恢复后补算。连续心跳相隔超过五秒时，将该间隔视为进程长暂停，不补算。独立时钟线程避免慢业务结算误阻塞时间推进。

暂停边界以最后已提交的心跳为准，正常精度约一秒；长暂停以超过五秒的心跳间隔识别。故障恢复只处理游戏时间上已到期的活动，不能因真实停机时长补跑战斗回合、扣除资源、完成队列、触发超时或作废对局。

多实例通过数据库行锁及五秒租约选出唯一推进者，其他实例只同步检查点；接管仅建立新锚点，不补算租约失联间隔。当前方案每个实例每秒查询检查点，不依赖玩家在线。

鉴权令牌、账号注销/恢复期限、封禁、合规开放日历、防沉迷、聊天限流、网络心跳、缓存与运维日志继续采用真实时间。这些不是游戏活动进度。

## 前端同步

HTTP 响应通过 `X-Game-Time` 返回游戏时间，完整状态也有 `serverTime`；WebSocket 建连、心跳及推送携带 `gameTime`。前端倒计时和进度条只读取服务器样本，不按本机时间外推。失联后保留最后样本，重连后继续。

WebSocket 的原 `timestamp` 仍为真实时间，不能作为活动时钟。前端忽略迟到的较小游戏时间样本；切换账号或大区时重置样本，避免跨时间轴比较。网络心跳按真实时间发送，业务租约、确认和回合截止按游戏时间判断。

只有客户端网络断开而服务器仍运行时，页面暂时停止更新，重连后同步实际进度。预计真实完成时刻按剩余游戏时长换算；后续停服会顺延。历史事件的时间字段保留原记录值。

## 部署与旧存档

需要同时部署新后端和前端，执行 Flyway `V106__persistent_game_clock.sql`，随后刷新浏览器资源。默认启用 `game.clock.enabled=true`；测试配置可关闭并显式安装可控时钟。关闭该配置不是生产暂停开关：未安装其他时钟源时 `GameClock` 会回退真实时间；仅关闭 `game.scheduling.enabled` 也不会冻结游戏时钟。首次升级旧版没有全服心跳，使用玩家最大 `last_tick` 与真实当前时间中的较小值作为最近运行点，无有效玩家结算记录时使用当前真实时间；无法精确追溯旧版强杀时刻，最多保留旧版最后结算到实际停机之间的时间差。此后重启直接使用持久化检查点。

不要删除 `game_clock`、手工把它改为真实当前时间或改回旧版墙钟结算，否则会把已暂停时长计入活动。

## 验证

### 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 行军剩10分钟，停服2小时后重启 | 恢复后仍剩约10分钟，停服期间不抵达、不交战、不返城 |
| 采集、建筑、科研、造兵、装备生产进行中停服 | 采集收益和队列进度冻结，恢复后按剩余游戏时长继续 |
| 世界战斗／PvP指挥窗口、匹配确认或业务租约未到期时停服 | 恢复后保留剩余窗口，不因停机超时、跳回合或作废 |
| 玩家离线或全区没有玩家在线，服务器正常运行 | 游戏时钟继续，按既有规则推进活动和离线结算 |
| 仅客户端断线，服务器继续运行 | 本地显示停留在最后样本；重连同步实际进度 |
| 数据库故障、进程长暂停、强制终止或多实例接管 | 以持久化检查点恢复，不补失联时长，不由多个实例重复推进 |
| 停服跨过真实北京时间刷新点或零点 | 游戏周期与日额度不提前刷新；恢复后到达游戏边界才触发 |
| 首次升级无全服心跳的旧存档 | 按迁移锚点近似恢复，不宣称能精确追溯旧版停机点 |
