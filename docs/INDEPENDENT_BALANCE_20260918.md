# 自主兵种数值设计

历史规则版本：`balance-v4-independent-20260918`。本文保留自主推导的设计记录；当前数值、最低火力规则与验证见 [v5 微调](BALANCE_TUNING_20260918.md)。本文链接的设计输入和推导脚本已随 v5 更新。

## 设计边界与输入来源

参考通用军事兵种分工及前述老游戏攻略中的定性思路：空战拦截、对地轰炸、装甲承伤、远程火力、防空护航。历史数值表不作为参数输入，也不整体缩放或换名复用。本文件记录本项目的数值选择与验证依据，不将其描述为原作数据或原作伤害公式。

本轮重算全部 17 个兵种、4 种工事的四项攻击。造价、生命、防御、速度、人口、耗粮和后勤载重沿用本项目此前的配置基线；射程按本轮职责调整装甲车、突击炮和火箭。未声称这些保留字段在本轮全部重新设计。兵种名称使用通用称谓，定位说明按本项目实际规则撰写。

四项攻击为对地、对空、对海、对工事。0 明确表示没有该武器能力：运输机无武装，潜艇仅攻击舰船，火箭不对空；轻坦和重坦保留很弱的对空自卫，不要求所有兵种都有所有武器。

## 可复现的攻击推导

输入清单：[attack-design.json](balance/attack-design.json)。每个非零攻击都记录参考目标、目标齐射轮数和适用专项倍率；`null` 明确表示无此能力。

以本项目的线性伤害公式为基础：

- 加权造价 `W = 钢铁 + 2 × 石油 + 4 × 稀矿`。
- 无科技目标的有效生命 `E = HP × (1 + 0.05 × 防御)`。
- 双方等预算 `B` 时，兵力分别为 `B/W攻方`、`B/W目标`。
- 希望满编攻方在不受反击、不移动的理想状态下，用 `V` 次齐射消灭目标，则 `攻击 = round(E目标 × W攻方 / (W目标 × V × 专项倍率))`。

资源权重和 V 是设计者选择的本项目假设，不是历史资料里的数据，也不是经过实盘验证的市场价格。V 用于指定“强项、弱项、自卫”的效率差异；不能把它当作实际战斗结束回合数。实际战斗还包含接敌时间、先手、战损衰减、科技、军官、城墙、取整与目标切换。

具体例子：

1. 装甲车对空：以轰炸机为参考，目标有效生命 192，加权造价分别为 240 和 840，V=1.75，倍率 1；得到 `round(192×240/(840×1.75))=31`。
2. 战斗机对空：同样以轰炸机为参考，自身加权造价 480，V=1.5，拦截倍率 1.15；得到 `round(192×480/(840×1.5×1.15))=64`。专项倍率已进入推导，不重复施加泛化对空增益。
3. 轰炸机对地：参考重坦，有效生命 1680，双方加权造价均 840，V=15，反重坦倍率 2；得到 56。
4. 突击炮攻坚：参考碉堡，有效生命 572，加权造价为 280 对 80，V=12；得到 `round(572×280/(80×12))=167`。工事造价低且耐久高，因此攻坚数值与对地数值不能直接比较强弱。

攻坚效率需要适配 30 回合上限：纯突击炮从玩家交战距离 3000 接近到射程约需 14 回合，因此将理想攻坚齐射目标设为 12；火箭射程更远，设为 16；轰炸机机动更快，设为 14。这些目标还用实际战斗验证，不只检查公式能否算出一个数。

数值推导脚本只读取设计输入和本地定义，不改写配置或格式：

```sh
node scripts/balance/derive-attacks.cjs
node scripts/balance/derive-attacks.cjs --json
```

不带参数时，同时核对结果与前端配置是否一致，不一致以非零状态退出。后端 `AttackDesignTest` 另外核对设计输入与 Java 参数、实际目标领域和专项倍率；前端契约测试核对两端所有属性。

## 射程与专项克制

装甲车射程从 180 调到 300，能够参与防空护航；突击炮射程从 400 调到 360，承担远程多用途支援；火箭从 400 调到 440，突出远程反重装甲，但仍怕快速渗透和空袭。速度仍按现有引擎每回合 `速度×50` 的移动尺度计算。实际射程适用于该兵种的所有武器，当前未拆分不同武器射程。

其余专项倍率沿用本项目此前的平衡规则；本轮给火箭增加对火炮类 ×1.5，以形成对突击炮的可用反制。火箭和轰炸机原先对碉堡的通用工事倍率取消，改由 `atkFort` 定义攻坚能力。反炮兵专长仍可作用于火炮类工事，例如特种兵对榴弹炮使用攻坚69再乘专项倍率2；目标领域与专项类别分别计算。

## 结算契约

伤害仍为 `当前目标攻击 × 剩余攻击份额 × 攻击加成 × 专项倍率 × 100/(100+5×有效防御)`，没有攻击平方或贴脸翻倍。攻击工事时一律读取 `atkFort`，包括同时属于火炮类的榴弹炮、反坦克炮和防空炮。

一轮行动的所有武器共享额度，目标全灭才使用剩余部分切换到下一个目标；切换领域必须重取武器、防御和专项倍率。例：32 门火箭先击毁 1 辆重坦，消耗 `420/(40×2.5/4)=16.8` 份，余下 15.2 份攻击碉堡时改用攻坚179，伤害约为 `15.2×179/2.2=1236.73`，不是继续用对地40或再打一轮完整齐射。

零攻击不会被科技、军官、连击或余伤变成可攻击武器。卡车的对地自卫不能用于拆工事。无法攻击任何目标时待命，30 回合耗尽后攻方撤退，保留实际幸存者。

经验和概览战力使用 `peakTroopAttack()`（对地、对空、对海三项最高值）。攻坚针对廉价高耐久工事单独定标，不混入这个估值，避免仅因攻坚面板较大而抬高兵种经验价值；概览战力不用于结算胜负。侦察专用交战继续读取侦察机对空攻击。

军队、城防面板与战报均展示对应攻击类型；静态脚本缓存版本已更新。现有兵力、已生产成本、历史战报不迁移，部署后的新结算使用新规则，进行中的行军也会使用到达时运行的服务端规则。

## 验证与局限

- 后端全量：258 项中 257 项通过、1 项跳过；跳过项为需要 `WARGAME_TEST_MYSQL_URL` 的 MySQL 迁移测试。
- 前端全量：150 项通过；包含全部单位/城防的四项攻击、其他面板属性及造价与 Java 定义一致性。
- 独立推导核对通过：21 个单位/工事的 84 个攻击字段与设计输入一致；参考目标领域、专项倍率与真实战斗规则一致。
- 主要克制矩阵：17 组关系 × 5 种预算（原始资源、加权资源、人口、生产时间、数量）× 2 种交战距离 × 2 档成长 × 32 个种子 × 互换攻守，合计 21,760 场，输出 `backend/target/balance-summary.csv`。
- 经济预算的 136 个场景全部通过预设 75% 全歼胜率门槛：134 个场景为 64 胜，2 个场景为 62 胜、2 负，无超时。其余预算仅报告结果，不要求便宜单位在等数量下击败贵单位。
- 14 个直接战斗兵种均能找到等原始资源的反制单位；侦察机、卡车、运输机不按直接作战兵种验收。
- 额外 320 场编成/攻坚对照：三种攻坚单位在约 56,000 加权预算下，对 700 座碉堡的两档成长场景均通过至少 24/32 场全歼要求；装甲车120+轰炸机25的混编预算49,800，少于纯轰炸机60的50,400，在对战斗机100的两档成长场景中均达到至少24/32胜，且优于纯轰炸机。
- 结算回归：四种工事均使用攻坚攻击，攻守双方一致；跨地面/空中/工事的剩余攻击份额守恒；零攻坚不能从对地自卫继承；攻击科技线性增长、技能、重坦掩护、渗透、射程、城墙、侦察、行军和伤兵相关测试通过。
- `git diff --check` 通过。未运行自动格式化，未部署、重启服务或提交代码。

这些结果证明本轮预设场景中的定位和规则可用，不证明任意混编、不同成长差、全部城防组合或长期经济都已平衡。工事攻坚基准目前主要覆盖纯碉堡；“能清除碉堡”不等于能直接突破配有防空、驻军和城墙的完整城市。资源权重、人口和生产时间之间仍有取舍，需继续观察实际玩法，不将这组模拟用于宣传必胜或全局平衡。
