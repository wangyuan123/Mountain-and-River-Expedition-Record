# QQ 邮箱绑定与密码找回设计

状态：已在工作区实施，发布与验证边界见 [实施说明](QQ_EMAIL_ACCOUNT_RECOVERY_IMPLEMENTATION.md)。尚未执行线上迁移或验证真实邮件收件；下文保留设计依据。

核心方案：新账号注册必须验证 QQ 邮箱；历史账号登录后补绑；忘记密码时通过已验证邮箱设置新密码。密码重置后退出全部设备，继续使用原账号和原游戏存档。

## 1. 当前系统与改动依据

| 位置 | 当前行为 | 设计要求 |
| --- | --- | --- |
| `frontend/js/main-view.js`、`frontend/js/main.js` | 注册只有用户名、密码、确认密码；“忘记密码”仅提示正在建设 | 增加注册邮箱验证与找回流程，沿用登录页和弹窗 |
| `AuthDtos.RegisterRequest`、`AuthController`、`AuthService` | 服务端注册未要求邮箱 | 服务端强制验证，不能仅依靠页面必填 |
| `Player`、`PlayerRepository` | 没有恢复邮箱字段及唯一性约束 | 增加已验证邮箱及数据库唯一约束 |
| `AuthService`、后台玩家管理 | 当前工作区存在保存、返回明文密码及把重置密码写入审计的逻辑 | 停止保存和展示明文，清理现存明文及相关日志暴露点 |
| `JwtAuthenticationFilter`、`AccountService` | 已有持久化 `authVersion`、账号行锁与提交后断开连接机制 | 密码重置、邮箱换绑复用这些机制 |
| `docs/SERVER_REGIONS.md` | 大区独立实例、独立数据库，同名账号可在不同区存在 | 邮箱绑定与找回始终属于所选大区 |
| `backend/pom.xml`、`RateLimiter` | 尚未引入邮件依赖；现有限流为进程内存实现 | 增加邮件发送适配；邮箱验证码及关键限额持久化 |

游戏内站内信继续由现有邮件系统处理。QQ 验证邮件走独立的外部邮件服务，不向站内信投递验证码。

## 2. 产品规则

| 项目 | 第一版规则 |
| --- | --- |
| 可绑定地址 | 完整的 `@qq.com` 邮箱，支持数字地址和符合地址规范的英文别名；必须实际收码验证 |
| 地址处理 | 去除首尾空白，统一大小写；严格解析单个地址并校验域名；不擅自删除本地部分的字符 |
| 唯一性 | 同一大区内，同一个规范化邮箱地址只绑定一个账号；不同大区可重复使用 |
| QQ 别名 | 不承诺识别同一 QQ 邮箱的多个别名为同一实际收件箱；唯一约束针对地址，不是自然人 |
| 邮箱用途 | 绑定、换绑、密码找回及必要安全通知；登录继续使用用户名和密码 |
| 新账号 | 注册时必须通过邮箱验证码验证，成功前不创建账号、城市或资源 |
| 历史账号 | 保留正常登录和游戏权限；登录后提示补绑，设置中保留长期入口 |
| 验证码 | 6 位数字，5 分钟有效，同一验证流程只接受最新一封的验证码 |
| 首次绑定 | 当前登录态 + 当前密码 + 新邮箱验证码 |
| 忘记密码 | 所选大区 + 用户名 + 已绑定 QQ 邮箱 + 验证码 + 新密码 |
| 邮箱换绑 | 当前密码 + 原邮箱验证 + 新邮箱验证；完成前原邮箱始终有效 |
| 解绑 | 第一版不提供单独解绑，避免账号重新失去找回能力 |
| 游客、机器人 | 不开放邮箱绑定和自动找回；游客转正式账号需要单独的进度迁移方案 |
| 已忘密码且未绑邮箱 | 无法凭新填的邮箱证明账号归属；提供现有官方支持渠道，不开放自行补绑入口 |

只支持 `qq.com` 是第一版产品范围，暂不扩展 `foxmail.com`、其他域名或 QQ 授权登录。后续扩展通过配置和明确规则实现。

## 3. 页面与操作流程

### 3.1 新用户注册

沿用当前登录页的“注册账号”模式，字段顺序为：

```text
服务器大区    [江苏一区                 ]
用户名        [                         ]
密码          [                         ]
确认密码      [                         ]
QQ 邮箱       [完整邮箱，例如 123456@qq.com]
邮箱验证码    [6 位数字        ] [获取验证码]

请绑定本人长期使用的 QQ 邮箱，忘记密码时用于找回账号。

[注册]
```

1. 页面检查用户名、密码及邮箱格式后请求验证码；这一步不创建账号，不提交密码。
2. 服务端返回验证流程编号和重发时间，页面显示“发送请求已提交，请检查邮箱及垃圾箱”，启动重发倒计时。SMTP 接受不代表收件箱已收到。
3. 玩家填写验证码并点击注册，继续展示当前用户协议确认弹窗；确认后一次提交注册资料、邮箱、验证码、流程编号和最新协议版本。
4. 服务端验证全部条件，在同一事务中创建账号、绑定邮箱并消费验证码。角色初始化和实名准入沿用现有约束；失败时不留下半成品账号或额外资产。
5. 成功后按现有流程登录。使用绑定确认通知告知玩家，但通知发送失败不撤销已完成注册。

修改用户名、邮箱或大区后，清除当前验证码和流程编号，要求重新获取；不能把旧流程用于新注册资料。协议弹窗确认提交时必须核对仍是同一份注册资料。

新建密码由前后端共同校验：第一版沿用当前页面 6—64 个字符的范围，同时限制 BCrypt 输入不超过 72 个 UTF-8 字节，不静默截断、不去除密码首尾空白。历史密码登录不因新建密码规则改变而失效。

### 3.2 历史账号补绑

在“设置 → 账号与安全”增加一行：

```text
QQ 邮箱    未绑定                         [立即绑定]
绑定后可在忘记密码时找回账号。
```

绑定弹窗包含“当前密码、QQ 邮箱、邮箱验证码”。发送验证码前检查当前密码，提交绑定时再次核对密码和登录版本，避免旧验证流程继续生效。绑定成功后显示脱敏地址及绑定时间，不在地图、排行榜、好友或公开档案中展示邮箱。

登录后，对尚未绑定的正式账号显示可关闭提示：“建议绑定 QQ 邮箱，忘记密码时可找回账号。”同一账号同一大区默认每天最多主动提醒一次；设置入口常驻。提醒关闭状态不作为服务端绑定状态。

首次绑定成功发送确认通知，不强制退出正常会话；此前签发的相关验证码同时失效。

### 3.3 忘记密码

“忘记密码”入口改为独立的找回表单，明确显示当前大区，分为两步：

1. 输入用户名和完整的已绑定 QQ 邮箱，点击获取验证码。
2. 输入验证码、新密码、确认新密码，点击“重置密码”。

未登录的发送入口统一返回：“若该账号已绑定此邮箱，验证码将发送至该邮箱，请检查收件箱及垃圾箱。”不返回账号存在性、绑定状态、邮箱片段或注销状态；不因账号与邮箱不匹配返回不同结果。

成功后显示：“密码已重置，所有设备已退出，请使用新密码登录。”不自动签发游戏 Token，不显示或发送原密码。使用当前密码登录的旧会话失效；游戏存档保持原样。

网络中断时不自动重复提交最终写请求。若结果不明，提示使用新密码尝试登录；绑定结果可重新登录后在设置中查询，注册结果可返回登录确认。

页面提供：“未绑定邮箱或邮箱无法使用？请通过官方渠道联系支持。”仅在配置了实际支持地址时展示链接，不编造联系方式或承诺一定找回。

### 3.4 邮箱换绑

已绑定时显示“QQ 邮箱：12***89@qq.com [更换邮箱]”，短地址也必须隐藏部分字符，普通页面不提供完整地址查询接口。

1. 玩家输入当前密码，验证码只发送到服务端记录的原邮箱。
2. 玩家输入原邮箱验证码及目标 QQ 邮箱；验证成功后取得 15 分钟内有效的专用换绑凭据。
3. 使用该凭据发送目标邮箱验证码；新验证码仍按 5 分钟计时，且不得超过换绑凭据剩余有效期。
4. 新邮箱验证成功后，在同一事务中完成唯一性检查、地址替换、版本更新及全部相关凭据消费。
5. 换绑成功退出全部设备，通知原邮箱和新邮箱，玩家重新登录。

换绑凭据绑定当前账号、原邮箱版本、目标邮箱和登录版本，不能修改目标后继续使用。凭据有效期内允许按限额重发新邮箱验证码，只在完成一次换绑时消费凭据。换绑未完成、超时或失败时不替换原邮箱、不提前占用新邮箱；最终提交时检查占用冲突。

原邮箱不可使用时转官方支持审核，不提供只凭登录态或当前密码跳过原邮箱验证的快捷换绑。

交互复用现有输入框、按钮、弹窗、主题和布局约定，不新增组件外观覆盖。错误信息留在相应字段附近，支持标签关联、验证码粘贴、键盘操作和读屏播报。切换大区、账号或关闭弹窗时清除密码、验证码及换绑凭据。

## 4. 数据设计

### 4.1 已验证邮箱

在 `players` 增加以下字段，或等价地拆为以 `player_id` 为主键的账号安全表；第一版建议在 `players` 增加字段，以复用账号锁：

| 字段 | 用途 |
| --- | --- |
| `recovery_email_cipher` | 完整规范化邮箱的加密值，用于投递 |
| `recovery_email_key` | 规范化邮箱的 HMAC 查询值，建立唯一索引，未绑定为 NULL |
| `recovery_email_verified_at` | 首次验证或最近换绑成功的服务端时间 |
| `recovery_email_version` | 默认 0，每次绑定、换绑递增，使旧凭据失效 |

加密字段和查询键禁止直接序列化，账号接口通过 DTO 返回 `emailBound`、`maskedEmail`、`verifiedAt`。已有账号默认未绑定，不回填未经确认的地址，不修改账号名及现有密码哈希。

使用独立的邮箱加密和 HMAC 密钥，具备版本标记和轮换方案。查询键轮换须重新计算存量索引并维持唯一约束，不能直接更换密钥导致同一地址产生两套占用结果。

### 4.2 验证流程

新增持久化验证记录，包含：随机 `challengeId`、服务端大区、用途、主体键、账号编号或待注册用户名、目标邮箱密文及查询键、签发时 `authVersion` 与邮箱版本、验证码摘要、签发/过期时间、发送状态、失败次数、消费时间。

用途固定为 `REGISTER`、`BIND`、`RESET_PASSWORD`、`CHANGE_OLD_EMAIL`、`CHANGE_NEW_EMAIL`，不能混用。

- 验证码使用 `SecureRandom` 生成，保留前导零；仅保存带服务端密钥的 HMAC 摘要，摘要包含流程编号、大区、用途、目标和验证码，使用恒定时间比较。不能仅对六位码做普通哈希。
- `challengeId` 使用至少 128 位随机量，只负责定位流程，不单独代表验证成功。
- 通过唯一的主体/用途槽位和数据库锁维护当前有效流程；重发更换编号并让前一流程失效。注册按邮箱约束活动流程，账号操作按账号约束，不能靠更换请求编号绕过限制。
- 换绑授权凭据单独保存摘要、绑定范围、过期与消费时间；仅保存在当前页面内存，不写 localStorage、URL 或日志。
- 最终成功时，账号更新与验证码消费在同一个事务提交；失败不出现“验证码已用但密码未改”的结果。
- 验证失败次数必须实际提交；业务错误不能让事务回滚后清零。采用返回校验结果后统一提交的方式，不通过抛异常丢弃计数。

另设数据库限额记录及有界邮件投递队列。进程内 `RateLimiter` 可作为前置拦截，但验证码、每日限额和消费状态不能仅保存在内存。

## 5. 接口契约

所有接口沿用大区 API 路由和 `X-Game-Server` 校验；未登录请求体同时携带 `serverId`，与当前实例严格一致。路径均以 `/api/auth` 为前缀。

| 方法及路径 | 权限 | 主要输入及返回 |
| --- | --- | --- |
| `GET /server`（扩展） | 公开 | 保留 `id/name`，增加类型明确的功能能力：注册是否要求邮箱、绑定/找回是否启用、整体邮件服务是否可用 |
| `POST /register/email-code` | 公开 | `serverId, username, email`；返回通用受理结果、`challengeId, expiresAt, resendAt, serverNow` |
| `POST /register`（扩展） | 公开 | 原有字段 + `email, challengeId, emailCode`；注册成功返回现有登录结果 |
| `GET /email` | 当前正式账号 | 返回本人邮箱脱敏信息及绑定状态 |
| `POST /email/bind-code` | 当前正式账号 | `currentPassword, email`；验证当前密码后发码 |
| `POST /email/bind` | 当前正式账号 | `currentPassword, email, challengeId, emailCode`；完成首次绑定 |
| `POST /password/reset-code` | 公开 | `serverId, username, email`；始终返回通用受理结果及相同结构的流程信息 |
| `POST /password/reset` | 公开 | `serverId, username, email, challengeId, emailCode, newPassword`；成功只返回重置完成，不发登录 Token |
| `POST /email/change/old-code` | 当前正式账号 | `currentPassword`；向已绑定原邮箱发码，不接受客户端指定原地址 |
| `POST /email/change/authorize` | 当前正式账号 | `currentPassword, newEmail, challengeId, emailCode`；原邮箱验证后返回一次性 `changeToken, expiresAt` |
| `POST /email/change/new-code` | 当前正式账号 | `changeToken`；向凭据绑定的目标地址发码 |
| `POST /email/change` | 当前正式账号 | `changeToken, challengeId, emailCode`；完成换绑并退出全部设备 |

公开发送接口对于地址已占用、账号不存在、账号邮箱不匹配、状态不允许等情况也返回外观一致的随机流程编号和相同时间字段，不发送验证码。使用相同的异步受理路径，不让邮件同步耗时暴露账号匹配结果。

`SecurityConfig` 只新增上述确实公开的发送与重置端点，不放开整个 `/api/auth/email/**`。邮箱管理端点必须使用玩家身份，拒绝游客与管理员 Token 充当玩家身份。

错误结构沿用 `{ code, error, retryAfter }`。明确的格式错误可返回 `EMAIL_INVALID`；已认证的绑定冲突返回 `EMAIL_UNAVAILABLE`；未登录最终找回失败统一为 `RESET_VERIFICATION_FAILED`，不区分用户名、邮箱、账号状态或验证码哪项不匹配。限流返回 `RATE_LIMITED` 和重试时间；整体邮件不可用返回统一的 `MAIL_UNAVAILABLE`，不能因收件地址存在性改变响应。

账号安全响应使用 `Cache-Control: no-store`；密码、验证码、完整邮箱和换绑凭据不放进 URL、访问日志、异常详情、埋点或前端持久化缓存。

## 6. 邮件投递与限额

### 6.1 发件方案

增加 `spring-boot-starter-mail`，提供独立的邮件发送适配层。收件方支持 QQ 邮箱，不要求发件方必须是 QQ；优先使用运营可监控的事务邮件服务，也可使用已开通 SMTP 的专用 QQ 发件邮箱。

使用 QQ SMTP 时，部署核验 `smtp.qq.com`、465 端口和隐式 TLS，并启用证书与主机名验证；凭据使用发件账号的 SMTP 授权码。实际发送能力和额度以所选账号及服务当时的设置为准，不在代码中承诺固定发送量。

拟新增环境配置：`WARGAME_MAIL_HOST`、`WARGAME_MAIL_PORT`、`WARGAME_MAIL_USERNAME`、`WARGAME_MAIL_PASSWORD`、`WARGAME_MAIL_FROM`、TLS 模式及邮箱数据/验证码密钥。具体映射在实现时落到 Spring 配置；示例文件不填真实凭据，前端不接触这些配置。

### 6.2 投递一致性

1. 短事务内校验限额，更新活动验证流程，并写入邮件队列；提交后由工作线程投递，不持有玩家锁等待 SMTP。
2. 队列中的收件地址及验证码载荷必须加密，投递成功或过期后立即清除验证码载荷；验证码校验表只保留摘要。
3. 只有发送成功且流程仍为当前版本时标记可验证。以签发时刻计算 5 分钟期限，排队和重试不延长；过期任务不得继续发送。
4. SMTP 结果不明时有界重试同一封、同一验证码，不能重试时生成新码。允许投递端偶发重复邮件，但业务消费只能成功一次。
5. 密码重置或换绑的完成通知在事务提交后排队，通知异常不回滚已完成的账号操作。

验证码邮件标题包含游戏名、大区和用途，例如“【山河远征录·江苏一区】重置密码验证码”。正文包含操作用途、有效期、大区、验证码以及“请勿向他人提供验证码；如非本人操作可忽略”。不包含原密码、新密码、完整账号资料或兑换内容；模板不接受任意收件人列表和自定义正文。

### 6.3 默认限额

| 维度 | 初始值 |
| --- | --- |
| 同一邮箱验证码发送 | 至少间隔 60 秒，跨用途合计每小时 5 次、每日 10 次 |
| 同一账号验证码发送 | 跨用途合计每小时 5 次、每日 10 次 |
| 同一来源 IP 公开发码 | 每小时最多 20 次受理请求，另设短时突发限制 |
| 单个验证码错误次数 | 最多 5 次，达到后该流程失效 |
| 账号/注册邮箱验证错误 | 跨重发累计每小时 20 次，不能通过重发清零 |
| 邮件服务整体 | 配置每小时/每日投递上限、队列容量、暂停发送与告警阈值 |

限额为可配置起点，按实际收件成功率和共享网络情况调整。所有时间由服务端真实时钟计算，不使用游戏加速时钟；每日窗口按北京时间自然日记录。

邮箱级和账号级内部限额命中时，公开发码仍返回相同受理外观但不投递，避免暴露关联关系；所有候选地址均按统一规则计量。只有与账号匹配结果无关的 IP/全局请求限额公开返回 429。前端倒计时仅用于交互，最终以服务端计数为准。

来源地址只从受信任反向代理取得；由网关规范化转发头并限制后端直连，邮件接口不直接采用任意客户端自报的转发地址。

## 7. 密码、会话与并发

密码重置在短事务内按既定锁顺序取得玩家和验证记录，重新检查账号状态、邮箱版本、流程用途、服务端时间和剩余次数。账号更新、验证码消费、相关换绑/注销恢复凭据失效及 `authVersion + 1` 必须一起提交。

提交后调用现有 `WebSocketPushService.disconnectAccountAfterCommit`。HTTP 与 WebSocket 继续验证 `authVersion`，旧设备、旧标签页和重启后保留的旧 Token 均不能继续使用。防沉迷活动会话按账号结束并结算，保留累计时长及实名绑定，不能通过改密获得额外游戏额度。

`AccountOperationConfig` 当前对多数 `AuthController` 方法不加业务锁；新增邮箱方法必须进入专用的账号安全服务，在锁内重检当前主体和 `authVersion`，不能仅依赖 HTTP 过滤器先前的验证。账号安全操作不要求持有游戏时间许可，未实名或处于禁玩时段的玩家仍可保护账号。

管理员协助重置密码也必须调用相同的凭据更新与会话失效服务，不修改绑定邮箱、不恢复封禁、不延长注销期限。移除默认固定密码与“查看原密码”的产品行为；如保留人工重置，需审核、审计及一次性安全交付方案。

上线前处理当前工作区的明文密码实现：停止注册和后台重置时写入 `plainPassword`；移除玩家列表、重置响应和页面中的明文展示；停止将新密码写入审计。通过新的前向迁移清空并移除明文列，不覆盖已有 Flyway 迁移。对现存审计、导出及备份中的敏感值明确清理和保留周期，不能只清主表便宣称全部擦除。

## 8. 注销、封禁及数据保留

- `ACTIVE` 正式账号：允许首次绑定、换绑与密码重置。
- 未到期的 `PENDING_DELETION`：允许使用原绑定邮箱重置密码，但保留注销状态和原截止时间。重置后玩家用新密码登录，仍须经过现有“明确确认恢复账号”步骤；不自动撤销注销。
- 注销到期或 `DELETED`：不发送找回验证码、不允许重置；公开响应沿用统一格式，清理任务是否及时运行不改变截止时间。
- 运营封禁：邮箱重置不解除封禁；第一版对封禁账号不开放自动重置，由支持处理。使用与现有登录一致的有效状态判断，不另立相互冲突的状态来源。
- 注销受理、恢复、密码变更或邮箱变更时，使此前签发的相关验证码及换绑凭据失效。恢复期内保留邮箱占用；最终注销清理时清空邮箱密文、查询键、验证时间和待投递数据，释放地址用于其他账号。
- 验证码到期立即逻辑失效，待投递密文载荷同步清除；失效验证记录定时分批清理，默认最长保留 24 小时。限额记录在窗口结束后删除；必要安全审计只保留事件、内部账号编号、大区、脱敏地址、时间和结果，默认 30 天并可按运营实际要求配置。

## 9. 代码落点与上线顺序

建议新增 `AccountEmailService`、`PasswordRecoveryService`、`VerificationCodeService`、`AccountCredentialService` 和邮件适配/投递任务。控制器负责 DTO 与权限边界，验证码、邮件投递和游戏内站内信分开维护。

主要修改范围：

- 后端：`AuthDtos`、`AuthController`、`AuthService`、`Player`、`PlayerRepository`、`SecurityConfig`，以及账号注销清理和后台密码重置路径。
- 前端：`main-view.js`、`main.js`、`api.js`，新增独立的邮箱/找回交互模块并接入 `index.html`；邮箱状态按账号和大区隔离。
- 配置与迁移：增加邮件依赖、Spring 配置、部署环境映射、示例变量和新的 Flyway 迁移；迁移号在实施时按最新序列确定。
- 协议：更新注册告知与 `privacy.html`，说明邮箱用途、验证邮件服务、保留与删除方式；涉及协议变更时前后端同步更新协议版本。

实施顺序：

1. 先完成停止保存/返回明文密码和统一凭据失效服务，补齐数据库字段、验证记录、限额与投递任务。
2. 接通受控测试收件箱，完成注册、补绑、换绑、找回及注销兼容的联调；不向真实玩家批量发测试邮件。
3. 部署后端能力与前端完整入口，确认发件配置、实际收件及告警有效，再统一开启注册强制邮箱规则。
4. 新注册缺少邮箱字段的旧客户端返回明确的“页面版本已更新，请刷新后注册”；旧注册重载和测试参数不能创建未验证的正式账号。游客功能沿用现有范围，不能通过游客入口转成未验证的正式账号。
5. 提醒老玩家补绑，观察投递延迟、失败率、限额命中和补绑完成率；保留用户名密码登录。
6. 若邮件整体故障，暂停新注册和发码并说明稍后重试；既有密码登录继续可用。不得将关闭验证作为故障降级方式。

## 10. 验收标准

使用独立测试账号、受控收件箱和邮件适配替身进行功能验收，不对真实玩家发送验证邮件。

| 场景 | 完成条件 |
| --- | --- |
| 新注册 | 邮箱验证、协议确认与账号创建闭环完成；一次成功只创建一个账号及一份初始存档 |
| 历史补绑 | 旧账号可继续登录，绑定后正确显示脱敏邮箱，原有城市及资源不改变 |
| 正常找回 | 收码后设置新密码，可用新密码登录；旧会话退出，存档不改变 |
| 换绑 | 原、新邮箱均验证；完成前旧邮箱有效，完成后新邮箱可用于找回，两侧收到通知 |
| 大区 | 同一邮箱可在不同区使用，找回只影响所选区的原账号 |
| 状态兼容 | 未实名账号可进行账号安全操作；找回不撤销注销、不延长恢复期限、不解除封禁 |
| 邮件故障 | 界面反馈发送状态；过期任务停止投递，限额重启后保留，已完成账号操作不被通知故障回滚 |
| 数据与日志 | 常规接口只返回脱敏邮箱，凭据保持摘要或加密存储，日志与后台不出现密码或验证码 |
| 数据清理 | 注销完成清除邮箱绑定及待发验证码，限额和验证记录按设定期限清理 |

实施已补充邮箱流程及迁移集成测试、前端交互逻辑测试，并验证大区与既有账号流程；实际 SMTP 收件能力仍需部署方使用受控收件箱验收，详见实施说明。
