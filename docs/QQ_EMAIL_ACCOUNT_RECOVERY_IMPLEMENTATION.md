# QQ 邮箱绑定与密码找回实施说明

实现日期：2026-10-28。代码及测试已写入工作区；未重启线上服务、执行线上迁移或向真实邮箱发信。

## 已实现

- 新注册必须提交 QQ 邮箱验证码，通过验证才创建账号和初始存档；历史未绑定账号仍可用原密码登录。
- 注册页提供邮箱与验证码字段；登录页“忘记密码”可设置新密码；设置页支持补绑和原、新邮箱双验证换绑。
- 未实名或没有游戏时间许可的账号可从实名页面进入“QQ 邮箱与账号安全”。账号安全接口不开放游戏数据访问。
- 同一大区内规范化邮箱地址唯一，不同大区独立。邮箱支持数字地址与合法英文别名，第一版只支持 `qq.com`。
- 密码重置、邮箱换绑及后台改密递增持久化会话版本、结算原游戏许可、退出旧设备，不清空游戏存档、不撤销注销或解除封禁。
- 验证码 6 位、5 分钟有效、60 秒重发；发送配额和错误次数持久化。公开发码使用统一受理响应。
- 邮箱采用 AES-GCM 加密，查询键与验证码采用独立 HMAC 密钥；加密投递队列支持短事务、投递租约、有界重试与定时清理。
- 绑定、换绑和密码找回的最小安全事件写入既有审计表，仅记录内部账号、大区和事件类型，不记录邮箱、密码或验证码；这些事件默认保留 30 天。
- 删除 `plainPassword` 字段及后台明文输出，后台改密不再使用固定默认密码或将密码写入审计。迁移清除历史改密审计正文中的凭据内容。

## 部署配置

从 `.env.example` 对照配置以下变量，SMTP 授权码和密钥由部署方直接填入受控环境，不提交版本库或发到聊天中：

| 变量 | 内容 |
| --- | --- |
| `WARGAME_EMAIL_ENABLED` | 默认 `true`；关闭时暂停新注册及发码，原密码登录仍可用 |
| `WARGAME_MAIL_HOST` | QQ SMTP 默认 `smtp.qq.com`，也可使用运营自有事务邮件服务 |
| `WARGAME_MAIL_PORT` | 默认 `465` |
| `WARGAME_MAIL_SSL` | 默认 `true`，使用隐式 TLS；设为 `false` 时强制 STARTTLS |
| `WARGAME_MAIL_USERNAME` | 专用发件账号 |
| `WARGAME_MAIL_PASSWORD` | SMTP 授权码；使用 QQ 发件时不是 QQ 登录密码 |
| `WARGAME_MAIL_FROM` | 与 SMTP 账号权限一致的发件地址 |
| `WARGAME_EMAIL_DATA_KEY` | Base64 编码的独立 32 字节邮箱数据加密密钥 |
| `WARGAME_EMAIL_HMAC_KEY` | Base64 编码的另一把 32 字节摘要密钥 |
| `WARGAME_MAIL_HOURLY_LIMIT` / `WARGAME_MAIL_DAILY_LIMIT` | 默认 200 / 1000，按发件服务实际额度调整 |
| `WARGAME_MAIL_QUEUE_LIMIT` | 默认 1000 条待发/发送中任务 |
| `WARGAME_MAIL_TRUSTED_PROXIES` | 受控反向代理 IP 或 CIDR，逗号分隔；默认不信任转发头 |
| `WARGAME_SUPPORT_URL` | 实际官方支持 HTTPS 地址；未配置时不展示虚构链接 |

两把密钥分别用 `openssl rand -base64 32` 生成并备份。不能在已有邮箱数据时直接更换；当前密文格式为 `v1`，正式轮换需要实现带旧密钥读取、重加密及 HMAC 唯一索引重建流程。

`docker-compose.yml` 已透传上述配置。受信任代理必须覆盖 `X-Real-IP`，本仓库 Nginx 已采用该设置；不能填写包含非受控客户端的宽泛网段。默认仅按 TCP 来源限流，代理部署若未配置可信代理会把共享来源计入同一限额。对外网关应启用 HTTPS。

缺少发件配置或密钥时，不提供免邮箱注册降级。`GET /api/auth/server` 的 `accountSecurity.mailAvailable` 表示配置完整，不代表已经验证实际 SMTP 连通或收件成功。投递失败仅记录内部任务编号，需接入运维告警；整体故障可关闭发码，过期载荷清理仍继续执行。

## 数据库与发布

新增迁移 `V137__qq_email_account_recovery.sql`：增加恢复邮箱字段和唯一索引，创建验证/限额/投递表，删除明文密码列并清理历史改密审计内容。

1. 发布前备份数据库并保存两把邮箱密钥；检查生产当前 Flyway 版本，避免与其他未发布分支的迁移号冲突。
2. 先在独立数据库验证迁移与生产 MySQL 版本兼容。自动化迁移检查使用 H2 MySQL 模式，不替代目标环境的发布验证。
3. 确认 SMTP 发件权限和受控收件箱可收信后，停止旧版本写入并按大区部署新版后端及前端。Flyway 在新版启动时执行迁移。
4. 旧后端仍引用已删除的明文列，不能与新版混跑或直接回退启动。需要回滚时使用协调好的数据库/应用恢复方案，不能只替换旧 JAR。
5. 新前端资源已更新版本号。旧注册客户端会提示刷新页面；邮件服务未就绪时暂停新注册，历史密码登录不受影响。
6. 用运营拥有的测试账号完成注册、补绑、换绑和找回实收验收，再通知老玩家补绑。

业务实体不再保存明文密码；历史导出、应用日志与数据库备份需由部署方按实际保留周期处理。此迁移不会删除外部导出文件或已有备份。

## 验证方式与边界

后端验证覆盖真实控制器、验证码邮件队列、旧账号补绑、注册、换绑、找回、注销恢复期、会话版本、后台管理及既有游戏流程。SMTP 使用明确隔离的测试替身，测试数据保存在内存数据库。

前端验证覆盖注册凭据、大区变化、绑定、找回、双邮箱换绑、先断线后完成 HTTP 的时序、账号切换清理以及原有登录/注册协议流程。未新增或调整组件样式。

本次相关后端测试 61 项、前端测试 32 项通过；最终接入最小安全审计后，邮箱流程与迁移的 8 项后端测试再次通过。JavaScript 语法检查及本次改动范围的只读差异检查通过，未执行自动格式化或修复命令。

未完成的部署事项：填写真实 SMTP 凭据与密钥、目标 MySQL 发布验证、实际 QQ 收件验收、配置支持渠道和日志告警/保留策略。已忘记密码且从未绑定邮箱的旧账号仍需人工归属审核，代码不提供跳过审核的补绑入口。
